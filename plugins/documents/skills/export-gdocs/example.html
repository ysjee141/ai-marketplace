back-ent.order.api-kotlin 서비스 문서

상위 묶음: 통합원스탑

이 문서는 ent-order-api-prd/ent-order-worker-prd의 as-built 런타임 구성과 운영 시 확인할 사항을 다룬다. 설계 근거와 상세 구현은 다루지 않으며, 저장소의 docs/와 adr/을 참고한다. 모든 인프라·모니터링 정보는 AWS와 Datadog에서 직접 조회하여 확인했으며, 항목별 조회 기준일은 문서 끝의 "조회 이력" 표에 정리했다. 장애 상황이라면 "모니터링"과 "알려진 이슈 및 장애 대응" 절부터 본다.

한눈에 보기

  • 역할: NOL티켓의 주문·결제·예매를 처리하는 백엔드 API/워커다. 예비주문 생성부터 결제 승인, 취소·환불까지 전체 트랜잭션을 관리한다.

 

  • 배경: 기존에는 SQL Server 스토어드 프로시저(SP)에 주문·결제·예매 로직이 뒤섞여 있어서, 수정 영향 범위를 파악하기 어렵고 단위 테스트도 불가능했다. 이 서비스가 그 로직을 Kotlin 코드로 옮기고, 결제는 야놀자 통합 결제 플랫폼(NOL Payment)에 위임한다. 레거시 전환(탈레거시)의 출발점이 되는 시스템이다.

 

  • 구성: api(동기 REST)와 worker(배치·Kafka consumer)로 나뉜 Gradle 멀티모듈이며, 두 모듈을 독립적으로 배포한다("모듈 구성" 절 참고).

 

  • 담당: 조재현 / 엔터주문플랫폼.

 

먼저 볼 것:

  • 가상계좌 지연 입금 배치가 prd에서 DISABLED 상태다. 의도된 중단인지 확인되지 않았다("알려진 이슈 1" 참고).

 

  • release-staging/release-stage/release-preproduction 태그는 사용하기 전에 확인이 필요하다("cd.yml의 환경 태그 매핑"의 경고 참고).

시스템 구조

시스템 토폴로지

이 다이어그램은 ent-prd 클러스터의 ent-order-api-prd/ent-order-worker-prd 서비스를 AWS CLI(Teleport 경유, tsh aws ...)로 직접 조회하여 확인한 실제 런타임 토폴로지다. 조회에는 ecs describe-services/describe-task-definition, elbv2 describe-target-groups/describe-rules, rds/elasticache/kafka describe-* 명령을 사용했다.

토폴로지 다이어그램: diagram.png(GitHub) · 원본 diagram.drawio

  • 메인 컨테이너 외에 datadog-agent(APM)와 log_router(로그 라우팅) 사이드카가 함께 실행된다. 사내 ECS 표준 구성이므로 다이어그램에는 표시하지 않았다.

 

  • 시크릿은 Secrets Manager(api: prd/ent-order, worker: prd/ent-order-worker)에서 ECS Task Definition의 secrets 설정으로 주입된다.

 

  • api와 worker 모두 같은 내부 ALB(ent-prd-internal-lb)에 host-header 방식으로 등록되어 있다. worker의 역할(배치·Kafka consumer)을 생각하면 worker의 Target Group은 헬스체크와 내부 호출 용도로 보인다. 정확한 용도는 확인되지 않았다("확인이 더 필요한 부분" 참고).

 

이 서비스를 호출하는 서비스 (인바운드)

직접 호출자는 ent-onestop.gateway-kotlin(OneStop GraphQL BFF)이다. 코드와 AWS 양쪽에서 확인했다.

  • 코드: ent-onestop.gateway-kotlin의 client 모듈에 @OrderClient(config = "order")를 사용하는 PreOrderApi.kt, PaymentsApi.kt가 있다. 각각 /api/v1/pre-order, /api/v1/payments를 호출하며, order-api의 /v1/pre-order, /v1/payment 엔드포인트와 대응한다.

 

  • AWS: ticket-onestop-gateway-prd와 ent-order-api-prd가 같은 내부 ALB에 등록되어 있어서, 내부망에서 바로 통신할 수 있는 구조다.

 

전체 인바운드 체인은 다음과 같다. 각 홉을 AWS에서 확인했다.

순서구성요소역할
1CloudFront진입점(alias ordo.interpark.com 등)
2ent-auth-gateway-prd인증 게이트웨이(외부 ALB)
3onestop-v2-front-prdOneStop 프론트(외부 ALB)
4ticket-onestop-gateway-prdGraphQL BFF(내부 ALB)

  • CloudFront부터 OneStop 프론트까지 앞 구간의 라우팅 규칙은 이 문서의 범위 밖이며, ent-auth.gateway-kotlin 등 각 서비스의 서비스 문서에서 다룬다.

 

  • 이 서비스의 host-header는 ent-order-api.inpk.in이다.

 

  • 별도로 NOL Payment가 결제 완료와 가상계좌 입금 콜백을 위해 /v1/callback/nol-payment를 직접 호출한다(docs/project-overview.md 근거).

 

모듈 구성

이 저장소는 Gradle 멀티모듈 구조이며, 서로 의존하지 않는 두 모듈을 독립적으로 ECS에 배포한다.

모듈역할ECS 서비스
(root) src/동기 주문/결제 REST APIent-order-api
worker/배치(@Scheduled+ShedLock) / Kafka Consumerent-order-worker

 

  • 패키지 베이스는 api가 com.interparktriple.order이고, worker가 nol.ticket.order(feature-slice)다.

 

  • worker에는 동기 REST와 비즈니스 로직을 두지 않으며, api의 도메인 로직이 필요하면 코드를 복제하지 않고 HTTP 호출이나 이벤트로 위임한다.

 

  • 커넥션 풀도 모듈별로 분리되어 있다. 예를 들어 MSSQL 락 때문에 api의 MySQL 풀이 고갈되어도 worker는 영향을 받지 않는다. 이 장애 격리는 의도된 설계다.

 

api 모듈은 Layered + Hexagonal + CQRS 구조다.

  • api/: REST 컨트롤러, Command/Query 분리

 

  • shared/core/domain: 엔티티·값 객체

 

  • shared/usecase: 비즈니스 오케스트레이션

 

  • shared/infrastructure: JPA/MyBatis 레포지토리, Feign 아웃바운드, Kafka, Redis

 

  • batch/: 배치 잡

 

ID는 PreOrderId, CustomerOrderId, PaymentIntentId처럼 강타입 값 객체로 감싼다. OpenAPI 계약은 *Spec 인터페이스에 선언하고 Controller가 구현한다.

worker 모듈은 레이어가 아니라 기능별 수직 슬라이스(feature-slice) 구조다. 한 기능(예: deposit/)에 필요한 Kafka consumer, 배치 Job, outbox 엔티티/레포지토리, 설정을 같은 패키지에 모아서 응집도를 높인다.

핵심 기능

1. 이중 데이터베이스 운용: 신규 주문/결제 데이터(PreOrder, Payment, 할인·쿠폰)는 MySQL(ent_order)에 JPA+QueryDSL로 저장한다. 레거시 상품·좌석·예매·회원 데이터는 MSSQL(Ticket2000)에서 MyBatis로 읽는다.

2. Kafka 이벤트 기반 비동기 처리: 결제 완료와 예매 확정 사이를 이벤트로 느슨하게 연결한다("인프라 구성" 절 참고).

3. NOL Payment 결제 연동: 결제 초기화, 완료 콜백, 가상계좌 입금 콜백, 결제 취소, 영수증 조회를 처리한다. 결제 자체는 NOL Payment에 위임한다.

4. 복합 할인 처리: 쿠폰·바우처 등 여러 할인 수단을 조합한 결제를 지원한다. 취소할 때는 할인 수단별로 개별 환불한다.

5. 배치 Job: PreOrderExpirationJob(미결제 예비주문을 10분 경과 시 만료 처리하고 좌석을 해제)과 VirtualAccountDelayDepositJob(가상계좌 지연 입금 처리)이 있다.

보충 설명

  • ALB host-header: api는 ent-order-api.inpk.in/.inpark-ent.in을 사용하고, worker는 ent-order-worker.inpk.in/.inpark-ent.in을 사용한다.

 

  • Target Group: 둘 다 target type이 ip다. 헬스체크 경로는 api가 /api/v1/health이고, worker가 /health-check다.

 

  • 오토스케일링: api는 Target Tracking 정책 두 개로 조정된다. 평균 CPU 65%와 타깃당 ALB 요청 수 1,000건을 기준으로 삼고, 최소 25개에서 최대 60개 범위에서 동작한다(확장·축소 쿨다운 각 300초). worker는 오토스케일링 대상이 아니며 Task 3개로 고정되어 있다.

 

  • EventBridge 배치: 둘 다 api 이미지를 batch 프로필로 실행하는 예약 태스크다.

 

  • Aurora MySQL: Writer ent-order-db01-prod와 Reader ent-order-db02-prod로 구성되어 있다. ORDER_MYSQL_* 시크릿을 사용한다. ent-onestop.affiliate-service도 이 클러스터를 사용한다.

 

  • MSSQL: TICKET_MSSQL_* 시크릿을 사용한다. ent-onestop.affiliate-service와 공유하는 동일한 레거시 DB다.

 

  • Kafka 토픽: ENT Kafka(ent-common-kafka-prd)에서는 ent.order.approval-requested.v2, ent.onestop-seat.status-changed.v2를 사용한다. NOL Kafka에서는 pf-pay-composite-cancel-request를, Notification Kafka에서는 booking-notification을 사용한다. NOL Kafka와 Notification Kafka는 이 AWS 계정에서 클러스터를 찾지 못했다(그룹 공용 또는 타 계정 소속으로 추정된다).

cd.yml의 환경 태그 매핑

.github/workflows/cd.yml에서 직접 확인한 값이다. 조직 공통 표와 표기가 다른 곳이 있는데, 이 저장소가 공용 extract-envs 액션을 로컬화하면서 생긴 차이로 보인다(ENTPDM-6019).

release 태그(접미사 제외)환경Spring 프로필AWS Role
release-devdevelopmentdevDEV_AWS_ROLE
release-qaqaqaDEV_AWS_ROLE
release-stagingstaging매핑 없음PRD_AWS_ROLE
release-rcrelease-candidatercPRD_AWS_ROLE
release-stagestage매핑 없음-

release-staging/release-stage/release-preproduction 태그는 사용하기 전에 먼저 확인한다. cd.yml의 "Set Environment Profile" 단계가 development/qa/release-candidate/production 네 가지 환경에만 PROFILE을 설정하므로, 이 세 태그로 배포하면 PROFILE이 빈 값이 될 것으로 보인다. application-{env}.yml도 local/dev/qa/rc/prd 다섯 개뿐이라서 해당 환경용 설정 자체가 없다. 실제로 사용하지 않는 레거시 분기로 추정되며, 실사용 여부는 확인이 필요하다("확인이 더 필요한 부분" 참고).

동일한 태그로 두 가지 배포 방법을 사용할 수 있다.

1. 태그 push(기존 방식): /common-release가 만든 release-** 태그가 push되면, push-image/push-image-worker 잡이 태그 접미사(-api/-worker)를 보고 자신이 담당하는 컴포넌트의 배포 생략 여부를 판단한다. 접미사가 없으면 api, worker, 예약 태스크(deploy-sched)가 모두 배포된다.

2. workflow_dispatch 수동 실행(ENTPDM-6019): 기존 release 태그를 ref로 선택하여 GitHub Actions 화면에서 수동으로 실행한다. target(all/api/worker) 드롭다운으로 배포 대상을 선택한다. 환경 판별이 태그 기준이므로 ref는 반드시 release-* 형식이어야 한다.

IAM Role은 dev/qa 환경이 DEV_AWS_ROLE을 사용하고, staging/rc/production 환경이 PRD_AWS_ROLE을 사용한다(affiliate-service와 같은 패턴이다). CD 워크플로에는 Docker Hub 로그인 단계도 포함되어 있다.

브랜치 전략을 설명하는 문서는 저장소 안에서 찾지 못했다. main 브랜치를 기반으로 작업하는 것으로 보인다. PR 자동화(pr-review-labeler.yml, pr-review-assinger.yml)는 워크플로 파일로만 확인했으며, 세부 규칙은 확인이 필요하다.

알려진 이슈 및 장애 대응

api와 worker는 장애 도메인이 분리되어 있다("모듈 구성" 절 참고). 그래서 한쪽 모듈만 이상이 있는 상황은 정상적인 격리 동작일 수 있다. worker가 담당하는 배치·Kafka 처리가 지연되면, worker 태스크와 EventBridge Rule 상태부터 확인한다.

1. 가상계좌 지연 입금이 처리되지 않는다.

  • 현상: ent-order-virtual-account-delay-deposit-prd EventBridge Rule이 prd에서 DISABLED 상태다(2026-08-31 확인).

 

  • 원인: 확인되지 않았다. 의도된 중단인지 실수인지 알 수 없다.

 

  • 대응: 먼저 담당자에게 의도 여부를 확인한다. 켜져 있어야 하는 규칙이 꺼져 있는 것이라면 긴급히 조치한다.

 

2. 일부 외부 연동에서 장애가 전파될 수 있다.

  • 현상: 외부 연동의 장애가 이 서비스의 지연과 실패로 이어진다.

 

  • 원인: Circuit Breaker(Resilience4j)가 전체 연동에 적용된 것이 아니다. README 자체에 "아직 적용되지 않은 외부 연동이 있을 수 있다"고 명시되어 있다.

 

  • 대응: 장애를 조사할 때 해당 Feign 클라이언트에 Circuit Breaker가 적용되어 있는지 먼저 확인한다.

 

개발환경 및 빌드

사전 요구사항은 JDK 21과 Gradle 8.x 이상이며, 컨테이너를 실행하려면 Docker도 필요하다.

# 빌드
./gradlew clean build

# 로컬 인프라(MySQL) 실행
docker compose up -d

# api 애플리케이션 실행
SPRING_APPLICATION_JSON='{"key":"value"}' ./gradlew bootRun --args='--spring.profiles.active=local'

# 배치 실행 (예: preOrderExpirationJob)
SPRING_APPLICATION_JSON='{"key":"value"}' ./gradlew bootRun --args='--spring.profiles.active=batch-local --job.name=preOrderExpirationJob'

# worker 모듈만
./gradlew :worker:compileKotlin
./gradlew :worker:bootJar   # → worker/build/libs/ent-order-worker.jar

# lint
./gradlew ktlintCheck
./gradlew ktlintFormat

 

  • 환경변수는 AWS Secrets Manager의 dev/ent-order 시크릿을 참고하여 로컬에 설정한다.

 

  • 프로파일은 local/dev/qa/rc/prd 다섯 가지다. api용(application-{env}.yml)과 배치용(application-batch-{env}.yml)이 분리되어 있다.

 

  • affiliate-connector-sdk(GitHub Packages)를 의존성으로 받는다. 빌드할 때 read:packages 권한이 있는 조직 PAT 인증이 필요하다(CI에서는 INTERPARK_ENT_TOKEN을 사용한다).

확인이 더 필요한 부분

저장소, AWS, Datadog 조회만으로는 근거를 찾지 못한 항목이다. 팀 내부 채널이나 nol-cloud-engineering/nol-actions 저장소에서 추가로 확인해야 한다.

  • 가상계좌 지연 입금 EventBridge Rule이 DISABLED인 이유. 상태는 알려진 이슈 1에 정리했고, 사유 기록은 찾지 못했다. 담당자에게 의도 여부를 확인하고, 결론을 이 문서와 저장소 문서에 남긴다.

 

  • ent-order-worker-prd Target Group의 실제 용도. 헬스체크 용도로 보이지만 근거가 없다. ALB 리스너 규칙과 worker의 HTTP 엔드포인트를 대조하여 확인한다.

 

  • worker를 대상으로 하는 모니터링의 존재 여부. Datadog 모니터 검색에서 찾지 못했다. 배치·Kafka 처리 이상을 감지하는 알림이 다른 이름으로 있는지 담당자에게 확인하고, 없다면 신설을 검토한다.

 

  • NOL Kafka와 Notification Kafka의 클러스터 식별자. 이 AWS 계정에서는 클러스터를 찾지 못했다. 그룹 공용 인프라 담당자에게 문의하거나, 시크릿에 저장된 bootstrap 서버 값으로 확인한다.

 

  • MYINFO_API_*와 EFIN_POINT_X_AUTHORIZATION의 연동 대상. 시크릿 키 이름만 확인했다. 코드의 Feign 클라이언트 설정과 담당자 확인으로 용도를 파악한다.

 

  • release-staging/release-stage/release-preproduction 태그의 실사용 여부. 배포 이력에서 사용 기록을 확인하고, 사용하지 않는 분기라면 cd.yml에서 제거를 검토한다.
