# 기술 문서 작성 지침 (ASD-STE100 기반 + 한국어 특화)

이 문서는 기술 문서를 작성·검토할 때 기준으로 삼는 글쓰기 지침입니다. PRD, TDD, 분석 문서, Jira 이슈, Pull Request 같은 기술 문서를 AI로 생성할 때 사람이 읽기 좋은 결과를 얻기 위한 규칙을 정리했습니다.

ASD-STE100은 영어를 대상으로 만든 표준이라, 일부 규칙은 한국어에 그대로 맞지 않습니다. 1부는 원 규칙의 취지를 한국어로 옮긴 것이고, 2부는 한국어에 맞춰 보완한 규칙입니다. 3부는 문서 단위의 구성 규칙입니다. 1부와 2부가 문장 단위 규칙이라면, 3부는 문서 단위 규칙입니다.

이 문서 자체도 아래 규칙을 지켜서 작성했습니다.

## 1부. ASD-STE100 핵심 규칙 (한국어 각색)

**단어**

- 한 개념에는 하나의 용어만 씁니다. 같은 대상을 여러 이름으로 부르지 않습니다. 같은 동작도 하나의 동사로 통일합니다.
- 한 단어를 한 가지 뜻으로만 씁니다. 여러 뜻으로 해석될 수 있는 단어는 피합니다.
- 정착된 기술 용어와 고유 명사는 그대로 씁니다. 억지로 풀어쓰지 않습니다.
- 슬랭, 은어, 임의 축약을 피합니다.

**명사구**

- 명사를 세 개 넘게 연달아 붙이지 않습니다. 예: "사용자 결제 정보 조회 처리 로직" 대신 "사용자의 결제 정보를 조회하는 로직".
- 조사로 명사 사이의 관계를 분명히 드러냅니다.

**동사와 태**

- 능동태를 씁니다. 수동태는 꼭 필요할 때만 씁니다.
- 지시문(절차)은 동작이 드러나는 서술형으로 씁니다. 예: "서버를 재시작합니다".
- 단순한 시제(과거, 현재, 미래)를 씁니다. 진행형이나 복잡한 시제는 피합니다.

**문장**

- 절차 문장은 20단어 안쪽, 설명 문장은 25단어 안쪽으로 짧게 씁니다. (한국어는 단어 대신 어절 기준으로 보면 편합니다.)
- 한 문장에 한 가지 지시만 담습니다.
- 수식어는 꾸미는 대상 바로 앞에 둡니다. 멀리 떨어뜨리지 않습니다.

**절차**

- 한 단계에는 한 동작만 씁니다.
- 조건을 먼저, 동작을 나중에 씁니다. 예: "빌드가 실패하면, 로그를 확인합니다".

**설명**

- 한 문단은 한 주제만 다룹니다.
- 한 문단은 여섯 문장을 넘기지 않습니다.
- 정보를 논리 순서대로 배열합니다.

**경고, 주의, 참고**

- 경고와 주의는 명확한 지시로 시작합니다. 이유나 배경은 지시 뒤에 붙입니다.
- 종류를 구분합니다. 경고는 사람에게 생기는 위험, 주의는 장비나 데이터 손상, 참고는 부가 정보에 씁니다.

**구성**

- 복잡한 정보는 목록으로 정리합니다.
- 괄호로 문장을 겹겹이 감싸지 않습니다.

## 2부. 한국어 특화 보완 규칙

ASD-STE100이 다루지 않는 한국어 특유의 문제를 보완하는 규칙입니다.

- **이중 피동과 과잉 피동을 쓰지 않습니다.** "되어집니다"는 "됩니다"로, "불려집니다"는 "불립니다"로 씁니다.
- **번역투를 피합니다.** "~에 대하여", "~를 통하여", "~에 있어서", "~를 가집니다"(have 직역), "~하는 것을 가능하게 합니다" 같은 표현을 우리말 어법으로 바꿉니다. 예: "성능에 대한 개선" 대신 "성능 개선".
- **명사화(개조식)를 문서 종류에 맞게 통일합니다.** Jira 제목이나 PR 제목처럼 짧은 곳은 명사형("~ 추가", "~ 수정")을 허용합니다. 본문 설명은 서술형("~합니다", "~입니다")으로 통일합니다. 한 문서 안에서 두 방식을 섞지 않습니다.
- **존댓말과 반말을 섞지 않습니다.** 문서 하나는 한 어투로 끝까지 유지합니다. 기본 어투는 3부의 "어투" 항목을 따릅니다.
- **행위 주체를 분명히 합니다.** 주어를 생략해서 "누가 하는지" 모호해지면 주어를 밝힙니다. 특히 시스템과 사용자의 동작이 섞이는 문장에서 주체를 명시합니다.
- **조사를 함부로 생략하지 않습니다.** "값 저장" 대신 "값을 저장합니다"처럼 조사를 살려 관계를 분명히 합니다. 단, 표나 제목처럼 관례상 생략하는 곳은 예외로 둡니다.
- **외래어와 영어 용어 표기를 통일합니다.** 처음 나올 때 "한글(English)" 또는 원어로 한 번 정하고, 문서 내내 같은 표기를 씁니다. 음차 남발(굳이 소리 나는 대로 적기)은 피합니다.
- **한자어를 겹겹이 쌓지 않습니다.** 쉬운 말로 바꿀 수 있으면 바꿉니다. 단, 정착된 기술 용어는 그대로 둡니다.
- **목록 항목의 형태를 맞춥니다.** 한 목록 안에서는 모든 항목을 같은 품사와 같은 종결 형태로 씁니다. 명사로 시작하면 전부 명사로, 동사로 끝내면 전부 동사로 맞춥니다.
- **조건절을 앞에 둡니다.** 한국어는 "~하면, ~합니다" 순서가 자연스럽습니다. (ASD-STE100의 조건 먼저 규칙과도 맞습니다.)
- **띄어쓰기와 외래어 표기법은 국립국어원 기준을 따릅니다.** 특히 복합 기술 용어의 띄어쓰기를 문서 안에서 통일합니다.

## 3부. 문서 구성 방식

핵심은 한 가지입니다. **근거를 먼저 보이고, 사실과 추정을 구분하고, 판단할 일을 끝에 모읍니다.**

**문서 머리**

- **첫 문단에서 문서의 목적과 범위를 선언합니다.** "이 문서는 ~을 다룹니다"로 시작합니다. 무엇을 다루고 무엇을 다루지 않는지 한 문단 안에 적습니다. 예: "이 문서는 주문 API의 운영 구성과 운영 시 확인할 사항을 다룹니다. 설계 근거는 다루지 않으며 설계 문서를 참고합니다."
- **조회 기준일을 밝힙니다.** 제목 맨 앞이나 첫 문단에 ISO 날짜로 적습니다. 예: "2026-07-06 2026-01 - 2026-06 사이의 AWS 비용 증가 분석", "2026-08-31 기준으로 AWS에서 조회했습니다." 조회한 자료는 시점이 지나면 틀릴 수 있으므로, 기준일이 곧 유효 범위입니다.
- **근거의 출처와 조회 방법을 링크와 함께 적습니다.** 데이터 출처와 원본 자료(스프레드시트, 대시보드)를 링크로 남기고, 어떤 명령이나 화면에서 조회했는지 적습니다. 예: "`aws ecs describe-services`로 운영 클러스터를 조회했습니다."

**본문 전개 순서: 근거 → 사실 → 해석 → 판단**

- **데이터를 먼저 보이고 관찰 사실을 목록으로 뽑습니다.** 차트, 다이어그램, 조회 결과 표를 먼저 두고, 그 아래에 "이 자료에서 다음 사실을 알 수 있습니다"로 사실을 열거합니다.
- **사실과 추정을 어미로 구분합니다.** 확인한 사실은 "~입니다", "~했습니다"로 끝냅니다. 추정은 "~로 추정됩니다", "~을 시사합니다", "~로 보입니다"로 끝냅니다. 한 문장 안에 사실과 추정을 섞지 않습니다. 예: "Task Definition은 rev. 3입니다."(사실) "캐시는 공용 Redis를 쓰는 것으로 추정됩니다."(추정)
- **확인하지 못한 것은 숨기지 않고 이유와 확인 방법을 적습니다.** 무엇을 확인하지 못했는지, 왜 못 했는지, 어떻게 확인할 수 있는지 세 가지를 한 항목에 적습니다. 예: "클러스터 메트릭은 보존 기간이 지나 확인하지 못했습니다. 보존 기간을 늘린 뒤 다시 조회합니다."
- **문제를 먼저, 방향을 나중에 씁니다.** 배경 설명은 "어떤 문제가 있었는지 → 그래서 무엇을 택했는지 → 그 결과 지금 구조가 어떤지" 순서로 씁니다. 방향성 문서는 "본질적인 어려움 → 상황적인 어려움 → 기회 → 해야 할 일" 순서입니다.
- **여러 항목을 열거할 때는 순서어와 볼드를 함께 씁니다.** "첫 번째로, **공급자 우위**라는 점입니다"처럼 항목의 핵심 구절을 볼드로 표시하고 이어서 설명합니다. 읽는 사람이 볼드만 훑어도 요지를 알 수 있어야 합니다.
- **각 항목의 상세는 라벨형 하위 목록으로 적습니다.** "상세 트렌드:", "특이사항:", "현황:", "상세 위치:" 같은 라벨을 붙여 하위 항목을 나눕니다. 같은 종류의 항목에는 같은 라벨 세트를 씁니다.

**수치와 강조**

- **수치는 절대값과 변화율을 함께 적습니다.** "$42,103.92에서 $97,937.80로 약 132.6%($55,833.88 증가)"처럼 시작값, 끝값, 증가율, 증가액을 다 적습니다. 리소스 스펙도 "desiredCount 50"처럼 숫자를 그대로 적고, 변경이 있었다면 이전 값과 함께 적습니다.
- **기간과 시점은 ISO 날짜로 적습니다.** "2026-01 - 2026-06", "2026-08-30"처럼 적습니다. "지난달", "최근" 같은 상대 표현은 쓰지 않습니다.
- **핵심 결론 구절만 볼드로 강조합니다.** 한 문단에 볼드는 한두 군데로 제한합니다. 볼드가 많아지면 강조 효과가 사라집니다.
- **영어 기술 용어와 리소스명은 원어로 적습니다.** ECS, NAT, private subnet, rationale처럼 원어를 그대로 씁니다. 2부의 표기 통일 규칙을 따르되, 억지 번역은 하지 않습니다.

**문서 마무리**

- **결론과 다음 액션을 분리해서 적습니다.** 결론 섹션에서 원인을 요약한 뒤, "다음 액션을 식별할 수 있습니다"로 할 일을 따로 열거합니다.
- **다음 액션은 판단 주체와 판단 기준을 담아 적습니다.** "~의 rationale을 확인하고 적절성 여부를 판단할 필요가 있습니다"처럼 무엇을 확인하고 무엇을 판단해야 하는지 적습니다. "검토 필요"만 적고 끝내지 않습니다.

**어투**

- **문서는 "~습니다" 경어체로 씁니다.** 한 문서 안에서 "~다" 평서체를 섞지 않습니다. 제목, 표 안, 짧은 목록 항목은 명사형으로 끝낼 수 있지만, 서술형으로 쓸 때는 본문과 같은 어투를 씁니다.

**작성 후 점검 목록**

- 첫 문단에 목적, 범위, 기준일이 있는지 확인합니다.
- 표와 다이어그램마다 조회 방법이 적혀 있는지 확인합니다.
- 추정한 내용에 "추정됩니다", "보입니다" 같은 어미가 붙어 있는지 확인합니다.
- 확인하지 못한 항목마다 이유와 확인 방법이 있는지 확인합니다.
- 수치에 단위, 기준일, 비교 대상이 있는지 확인합니다.
- 마지막 섹션이 결론과 다음 액션 목록으로 끝나는지 확인합니다.

## 참고

ASD-STE100은 한 문장에 한 가지, 능동태, 일관된 용어라는 세 축이 핵심입니다. 자세한 규칙을 다 외우지 않아도, AI에게 "ASD-STE100을 따라 작성해줘"라고만 해도 문장이 눈에 띄게 정돈됩니다. 여기에 2부의 한국어 규칙을 더하면 번역투가 줄고 읽기가 더 편해집니다. 3부까지 더하면 근거와 판단이 구분된 구조로 문서가 정리됩니다.
