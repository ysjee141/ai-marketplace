# 실행 모드

하네스는 **동일한 파이프라인·게이트·산출물**을 세 가지 실행 모드로 돌릴 수 있다.
모드는 "무엇을 하는가"가 아니라 **"누가 수행하는가"** 만 바꾼다.

토큰 예산과 품질 요구가 프로젝트마다 다르므로, 모드를 고정하지 않고 선택하게 한다.

## 1. 모드 정의

| 모드 | 위임 범위 | 서브에이전트 수 | 성격 |
|------|----------|----------------|------|
| **`skill`** (경량) | 없음 — 메인 세션이 역할을 순차 전환 | 0 | 토큰 최소. 스킬 문서가 절차를 보장 |
| **`balanced`** (균형·**기본**) | **게이트 리뷰 + 통합 QA만** 위임 | 작업당 3~7 | 판정 독립성만 확보하고 나머지는 메인이 수행 |
| **`agent`** (전체) | 분석·구현은 팀, 나머지는 서브에이전트 | 작업당 12~25 | 병렬성·교차검증 최대. 대규모 작업용 |

### `skill` 모드

메인 세션이 역할을 선언하고 전환하며 모든 단계를 직접 수행한다.
`harness/adapters/generic-agent.md`의 순차 대체 규약을 그대로 적용한다.

```
현재 역할: codebase-analyst
참조: .claude/agents/codebase-analyst.md, .claude/skills/codebase-analysis/SKILL.md
입력: _workspace/{slug}/01_planning/prd-draft.md
출력: _workspace/{slug}/02_analysis/02_codebase-analyst_impact.md
```

역할 전환 시 **이전 산출물을 반드시 파일로 저장하고, 새 역할은 파일에서 읽어 시작**한다.
컨텍스트로 넘기면 역할 경계가 흐려진다.

### `balanced` 모드 (기본)

**서브에이전트를 쓸 가치가 가장 큰 곳에만 쓴다.**

위임하는 것:
- **게이트 리뷰 (G1~G6)** — 생성자와 리뷰어의 분리가 판정 품질의 핵심이다.
  자기 산출물을 자기가 판정하면 반드시 관대해진다.
- **통합 QA** — 경계면 교차 검증은 선입견 없는 독립적 읽기가 유리하다.

위임하지 않는 것: 기획·분석·계획·설계·구현·테스트 — 메인 세션이 스킬을 읽고 수행.

### `agent` 모드

`harness/adapters/claude-code.md` 2절의 구성을 그대로 적용한다.
분석·구현은 에이전트 팀, 나머지는 서브에이전트.

## 2. 단계별 수행 주체

| 단계 | `skill` | `balanced` (기본) | `agent` |
|------|---------|-------------------|---------|
| 01 기획 | 메인 | 메인 | 메인 (사용자 대화 필수) |
| 02 분석 | 메인 (역할 2회 전환 + 교차 검토) | 메인 (동일) | **팀** (research + codebase) |
| 03 계획 | 메인 (역할 2회 전환) | 메인 (동일) | 서브 ×2 (순차) |
| 04 설계 | 메인 | 메인 | 서브 ×1 |
| 05 구현 | 메인 (Task 순차) | 메인 (Task 순차) | **팀** (영역별 + network + QA) |
| 05 QA | 메인 (별도 턴) | **서브 ×N** (모듈별) | 팀 내 QA |
| 06 테스트 | 메인 | 메인 | 서브 ×1 |
| **게이트 G1~G6** | 메인 (별도 턴, 파일만 읽기) | **서브 ×1/게이트** | 서브 ×1~2/게이트 |
| 07 배포 | 메인 | 메인 | 서브 ×1 |

**산출물 경로·형식·게이트 기준은 세 모드에서 완전히 동일하다.**
모드를 바꿔도 `_workspace/`와 `/docs/`의 구조는 달라지지 않는다.

## 3. 모드 선택 기준

| 상황 | 권장 모드 |
|------|----------|
| 토큰 예산이 빠듯하다 | `skill` |
| 버그 수정, 소규모 변경 (Task 5개 이하) | `skill` |
| 문서화만 수행 | `skill` |
| **일반적인 기능 개발** | **`balanced`** |
| 신규 프로젝트 초기 구축 | `balanced` |
| 리뷰 품질이 중요한 작업 | `balanced` 이상 |
| Task 15개 이상, 영역 3개 이상 동시 | `agent` |
| 프론트+백+DB가 동시에 얽힌 경계면 다수 | `agent` |
| 병렬 라운드가 3개 이상 (WBS 산출 결과) | `agent` |
| 대규모 마이그레이션·리팩터링 | `agent` |

### 자동 제안 규칙

오케스트레이터는 WBS 산출 후(03 계획 완료 시) 다음을 근거로 **모드 상향을 제안**한다.
자동 전환하지 않고 사용자에게 묻는다.

| 조건 | 제안 |
|------|------|
| Task ≥ 15 **또는** 필요 역할 ≥ 3 **또는** 병렬 라운드 ≥ 3 | `agent`로 상향 검토 |
| Task ≤ 5 이고 필요 역할 = 1 | `skill`로 하향 검토 |

## 4. 토큰 특성

> 절대 수치는 작업 규모·코드베이스 크기에 따라 크게 달라지므로 제시하지 않는다.
> 아래는 **동일 작업을 세 모드로 돌렸을 때의 상대적 특성**이다.

| 모드 | 상대 비용 | 비용이 드는 지점 |
|------|----------|----------------|
| `skill` | 기준 (1×) | 메인 컨텍스트가 길어짐 — 단계가 쌓일수록 누적 |
| `balanced` | 기준보다 높음 | 게이트마다 리뷰어가 산출물을 새로 읽음 |
| `agent` | 가장 높음 | 팀원마다 독립 컨텍스트. 팀 통신·조율 오버헤드 추가 |

### 비용을 만드는 실제 요인

| 요인 | 설명 |
|------|------|
| 컨텍스트 재적재 | 서브에이전트는 산출물·스킬을 처음부터 다시 읽는다. 이것이 대부분의 추가 비용 |
| 팀 통신 | `agent` 모드의 메시지 교환. 팀원 수에 대략 비례 |
| 게이트 재시도 | 반려되면 재작업 + 재판정. **모드와 무관하게 가장 큰 변동 요인** |

> **게이트 반려 1회의 비용이 모드 차이보다 클 수 있다.**
> 토큰을 아끼는 가장 확실한 방법은 모드 하향이 아니라 **앞 단계를 제대로 하는 것**이다.
> 기획·분석이 부실하면 어떤 모드에서도 뒤에서 반복 재작업이 발생한다.

### `skill` 모드의 컨텍스트 관리

단계가 쌓이면 메인 컨텍스트가 길어진다. 다음으로 완화한다:

- 각 단계 완료 시 **산출물을 파일로 저장하고 요약만 유지**한다
- 다음 단계는 필요한 파일만 다시 읽는다. 이전 단계 전문을 컨텍스트에 남기지 않는다
- 스킬은 필요한 시점에 읽고, reference는 해당 영역만 로드한다

## 5. 모드별 품질 보정

모드를 낮추면 **잃는 것이 생긴다.** 무엇을 잃는지 알고, 보정 절차를 적용한다.

### `skill` 모드에서 잃는 것과 보정

| 잃는 것 | 보정 절차 |
|---------|----------|
| **게이트 판정 독립성** | ① 리뷰는 반드시 **별도 턴**에서 ② **산출물 파일만 읽고** 생성 과정의 추론 참조 금지 ③ 체크리스트 **항목별 명시 판정** ④ **지적 표를 먼저 쓰고 판정 선언** |
| 병렬 분석의 교차 검증 | 두 분석을 각각 완성한 뒤 **교차 검토 라운드 1회**를 명시적으로 추가 (`_cross-review.md`) |
| 경계면 결함의 독립적 발견 | QA 시 **계약 문서 → 생산자 → 소비자** 순으로 읽고, 양쪽을 같은 응답에서 대조 |
| 구현 중 실시간 계약 동기화 | 계약 변경 시 `_workspace/{slug}/05_implement/_messages.md`에 기록하고, 영향받는 Task 착수 전 반드시 읽는다 |

### `balanced` 모드에서 잃는 것과 보정

| 잃는 것 | 보정 절차 |
|---------|----------|
| 영역별 전문 에이전트의 깊이 | 구현 시 해당 영역 `references/`를 반드시 로드한다 |
| 병렬 구현 | Task를 WBS 병렬 라운드 순서대로 순차 수행. 경계면 공유 Task는 **연속 배치** |

`balanced`는 게이트 독립성을 유지하므로 **품질 저하 위험이 가장 작은 절충안**이다.

## 6. 설정과 전환

### 저장소 기본값

`harness/config.yml`의 `execution_mode`가 기본값이다.

```yaml
execution_mode: balanced    # skill | balanced | agent | ask
```

`ask`로 두면 작업 시작 시 오케스트레이터가 매번 사용자에게 묻는다.

### 작업별 기록

작업 시작 시 결정된 모드를 `_workspace/{slug}/state.json`에 기록한다.

```json
{ "execution_mode": "balanced", "mode_source": "config" }
```

`mode_source`: `config` | `user` | `auto-suggested`

### 사용자 지시로 전환

사용자가 명시하면 config보다 우선한다.

| 발화 | 해석 |
|------|------|
| "가볍게 돌려줘", "토큰 아껴줘", "에이전트 쓰지 마" | `skill` |
| "제대로 돌려줘", "에이전트 다 써서", "병렬로" | `agent` |
| "리뷰는 따로 받고 싶어" | `balanced` |

### 작업 중 전환

**단계 경계에서만 전환한다.** 진행 중인 단계에서 바꾸지 않는다.
전환 시:

1. 현재 단계를 완료하고 산출물을 파일로 저장한다
2. `agent` → 하위 모드: 활성 팀을 정리한다 (`TeamDelete`)
3. `state.json`의 `execution_mode`와 `mode_source: "user"`를 갱신한다
4. `walkthrough.md`에 전환 시각·사유를 기록한다

산출물은 파일에 있으므로 전환해도 이어서 진행할 수 있다.

## 7. 불변 사항

**모드와 무관하게 다음은 절대 달라지지 않는다.** 모드는 토큰 예산 조절 수단이지
품질 기준의 완화 수단이 아니다.

1. 파이프라인 단계 구성과 순서
2. 게이트 체크리스트와 심각도 판정 규칙 (BLOCKER 1건 → REJECT)
3. 롤백 규칙 — 결함이 발생한 단계로
4. 게이트 3회 반려 시 자동 재작업 중단
5. 산출물 경로·템플릿·형식
6. `walkthrough.md`·`state.json` 갱신 시점
7. 모든 코드에 테스트 존재
8. E2E는 headless로만 실행
9. **실행하지 않은 것을 실행했다고 보고하지 않는다**
10. ADR 사용자 승인
11. 문서 승격은 사용자 승인 후

> 모드를 낮춰서 게이트를 건너뛰거나 체크리스트를 줄이는 것은 허용되지 않는다.
> 토큰이 부족하면 **모드를 낮추거나 작업 범위를 줄이되, 기준은 유지한다.**
