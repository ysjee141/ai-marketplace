# DDD 적용 원칙

DDD는 전면 도입 아니면 미도입인 이분법이 아니다. **서비스의 규모와 성향에 따라
적용 수준을 결정하고, 그 결정을 ADR로 남긴다.**

## 1. 적용 수준 판정

설계 단계 초입에 다음 축을 평가하여 **Level 0~3** 중 하나를 결정한다.

| 축 | 질문 | 점수 |
|----|------|------|
| 도메인 복잡도 | 업무 규칙이 CRUD를 넘어서는가? 불변식·상태 전이·정책이 있는가? | 0~3 |
| 언어 불일치 | 기획/개발/사용자가 같은 대상을 다른 이름으로 부르는가? | 0~3 |
| 수명 | 이 시스템이 1년 이상 유지·확장되는가? | 0~2 |
| 팀/모듈 수 | 독립적으로 작업하는 단위가 2개 이상인가? | 0~2 |

**합산 점수 → 적용 수준**

| 점수 | 수준 | 적용 범위 |
|------|------|----------|
| 0~2 | **Level 0 — 미적용** | 일반적인 계층 분리만. DDD 용어 사용 금지 (오히려 혼란) |
| 3~5 | **Level 1 — 유비쿼터스 언어만** | 용어집(glossary) 작성 + 코드 네이밍 통일. 전술 패턴 미사용 |
| 6~8 | **Level 2 — 전술적 설계** | 엔티티/값 객체/애그리게이트/리포지토리/도메인 서비스 도입 |
| 9~10 | **Level 3 — 전략 + 전술** | 바운디드 컨텍스트 분리 + 컨텍스트 맵 + 전술 패턴 전면 적용 |

판정 결과와 근거는 `docs/design/`의 설계서 서두와 ADR에 기록한다.
**"일단 Level 3으로 시작"은 금지한다.** 필요해지면 올린다.

## 2. 전략적 설계

Level 3에서 수행한다.

### 유비쿼터스 언어

- `docs/design/glossary.md`에 **용어 → 정의 → 코드 식별자** 3열 표로 작성
- 기획서(PRD)·설계서·코드·DB 컬럼·API 필드가 모두 이 표를 따른다
- 동의어 발견 시 하나로 통일하고, 표에 "폐기된 표현"으로 남긴다

### 바운디드 컨텍스트

컨텍스트 경계 후보를 찾는 신호:
- 같은 단어가 다른 의미로 쓰인다 (판매의 "상품" vs 물류의 "상품")
- 데이터 변경 주기가 확연히 다르다
- 담당 조직/팀이 다르다
- 트랜잭션 일관성이 요구되지 않는다

### 컨텍스트 맵

컨텍스트 간 관계를 다음 유형 중 하나로 명시하고 다이어그램으로 그린다:

| 유형 | 의미 | 사용 시점 |
|------|------|----------|
| Partnership | 양방향 협력, 함께 변경 | 같은 팀, 강한 결합 불가피 |
| Customer-Supplier | 상류가 하류 요구를 수용 | 조직상 우선순위 조정 가능 |
| Conformist | 하류가 상류 모델을 그대로 수용 | 상류가 외부/변경 불가 |
| **ACL (부패 방지 계층)** | 하류가 번역 계층으로 방어 | **외부 시스템 연동 시 기본값** |
| Shared Kernel | 공유 모델 | 최소화. 변경 비용 큼 |
| Published Language | 공개 스키마로 통신 | 다수 소비자 존재 |

**외부 API 연동은 예외 없이 ACL을 둔다.** 외부 스키마가 도메인 모델에
직접 침투하면 외부 변경이 도메인을 흔든다.

## 3. 전술적 설계

Level 2 이상에서 수행한다.

### 값 객체 (Value Object) — 가장 먼저 도입할 것

식별자가 없고 값으로 동등성이 결정되는 개념. **불변**이어야 한다.

도입 신호: 원시 타입(`string`, `int`)에 검증 규칙이 붙어 있다.

```
# 나쁨 — 이메일 검증이 여기저기 흩어진다
def register(email: str): ...

# 좋음 — 생성 시점에 불변식 보장. 이후 모든 곳에서 유효함이 보증됨
class Email:
    def __init__(self, raw: str):
        if not EMAIL_RE.match(raw): raise InvalidEmail(raw)
        self._value = raw
```

값 객체는 순수성 원칙과 완벽히 부합한다. **투자 대비 효과가 가장 큰 패턴이므로
Level 1에서도 선택적으로 도입할 수 있다.**

### 엔티티 (Entity)

식별자로 동등성이 결정되고 생애주기 동안 상태가 변한다.
상태 변경은 **의미 있는 도메인 메서드**로만 노출한다 (`order.cancel(reason)`),
setter를 열지 않는다.

### 애그리게이트 (Aggregate)

**일관성 경계**다. 다음 규칙을 지킨다:

1. 애그리게이트 루트를 통해서만 내부에 접근한다
2. **하나의 트랜잭션 = 하나의 애그리게이트 변경**
3. 애그리게이트 간 참조는 **객체 참조가 아니라 ID**로 한다
4. 크기는 작게 — "정말 같은 순간에 함께 일관되어야 하는가?"만 포함

경계 판정 질문: *"A를 바꿀 때 B가 즉시 일관되지 않으면 업무 규칙이 깨지는가?"*
- Yes → 같은 애그리게이트
- No → 별개 애그리게이트 + 도메인 이벤트로 최종 일관성

### 리포지토리 (Repository)

**애그리게이트 루트 단위로만** 정의한다. 인터페이스는 Application 계층(포트),
구현은 Infrastructure. 컬렉션처럼 보이게 설계한다 (`add`, `remove`, `findById`).

쿼리 전용 화면(대시보드, 목록 필터)에 리포지토리를 억지로 쓰지 않는다.
읽기는 **CQRS의 Query 측**으로 분리하여 DTO를 직접 조회해도 좋다.

### 도메인 서비스

엔티티/값 객체 어디에도 자연스럽게 속하지 않는 도메인 로직에만 사용한다.
**순수 함수로 작성한다.** 도메인 서비스가 늘어나면 모델링이 빈약하다는 신호
(빈혈 도메인 모델)이므로 엔티티로 로직을 되돌릴 수 있는지 먼저 검토한다.

### 도메인 이벤트

애그리게이트 간 결합을 끊는 수단. 과거형으로 명명한다 (`OrderPlaced`).
이벤트는 불변이며, 발생 시각과 애그리게이트 ID를 포함한다.
**애그리게이트는 이벤트를 반환만 하고, 발행은 Application 계층이 담당한다** —
순수성 유지를 위해서다.

## 4. DDD와 Clean Architecture의 접점

두 원칙은 충돌하지 않는다. 매핑은 다음과 같다:

| Clean Architecture | DDD |
|-------------------|-----|
| Entity 계층 | 엔티티, 값 객체, 애그리게이트, 도메인 서비스, 도메인 이벤트 |
| Use Case 계층 | 애플리케이션 서비스, 리포지토리 **인터페이스**, 트랜잭션 경계 |
| Interface Adapter | 리포지토리 **구현**, ACL 번역기, 컨트롤러, 프리젠터 |
| Infrastructure | ORM, 메시지 브로커, 외부 API 클라이언트 |

충돌이 생기면 **의존성 규칙이 우선**한다. DDD 패턴을 쓰기 위해 도메인이
프레임워크를 알게 되는 설계(ORM 어노테이션이 붙은 엔티티 등)는 허용하지 않는다.
ORM 엔티티와 도메인 엔티티를 분리하고 매퍼를 둔다. 이 분리가 과하다고 판단되면
Level을 낮추는 것이 옳지, 의존성 규칙을 깨는 것은 옳지 않다.

## 5. 흔한 오적용

| 오적용 | 증상 | 교정 |
|--------|------|------|
| 빈혈 도메인 모델 | 엔티티에 getter/setter만 있고 로직은 전부 서비스에 있음 | 불변식과 상태 전이를 엔티티로 이동 |
| 거대 애그리게이트 | 하나의 애그리게이트가 수십 개 엔티티 포함, 락 경합 발생 | ID 참조로 분해 + 도메인 이벤트 |
| 리포지토리 남용 | 화면마다 전용 조회 메서드가 리포지토리에 쌓임 | 읽기 전용 Query 모델로 분리 |
| 용어집 없는 DDD | 패턴만 쓰고 언어 통일 없음 — DDD의 핵심을 놓침 | glossary.md 먼저 작성 |
| CRUD에 DDD 강제 | 단순 설정 관리에 애그리게이트/이벤트 도입 | Level 0으로 하향, ADR 기록 |
