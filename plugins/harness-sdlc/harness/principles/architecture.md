## 1. 의존성 규칙 — 단 하나의 절대 규칙

> **소스 코드의 의존성은 항상 안쪽(고수준 정책)을 향한다. 안쪽은 바깥쪽을 절대 알지 못한다.**

이 규칙 하나가 Clean Architecture의 전부다. 나머지 규칙은 모두 이것의 파생이다.
"안쪽"은 비즈니스 규칙, "바깥쪽"은 그 규칙을 세상에 노출하거나 세상으로부터
데이터를 끌어오는 기계적 장치를 뜻한다.

이 규칙을 지키면 얻는 것:
- **테스트 용이성** — 도메인 로직이 DB·네트워크·UI 없이 실행된다. 테스트가 빠르고 결정적이다.
- **교체 가능성** — PostgreSQL → DynamoDB, REST → gRPC 전환이 도메인 코드를 건드리지 않는다.
- **AI 구현 용이성** — 각 계층이 독립적이므로 에이전트가 좁은 컨텍스트로 정확히 작업한다.

의존성이 바깥을 향해야 할 때는 **의존성 역전(DIP)** 으로 방향을 뒤집는다.
안쪽에 인터페이스(포트)를 선언하고, 바깥에서 구현(어댑터)한다.

```
[Entities] ← [Use Cases] ← [Interface Adapters] ← [Frameworks & Drivers]
   도메인       응용 규칙      컨트롤러/프리젠터/       웹/DB/외부API/UI
                              게이트웨이 구현체
```

## 2. 계층 정의

| 계층 | 담는 것 | 담지 않는 것 | 의존 대상 |
|------|---------|-------------|----------|
| **Domain (Entity)** | 엔티티, 값 객체, 도메인 이벤트, 불변식, 순수 도메인 서비스 | I/O, 프레임워크 타입, DTO, 어노테이션/데코레이터 | 없음 (언어 표준 라이브러리만) |
| **Application (Use Case)** | 유스케이스, 포트 인터페이스, 트랜잭션 경계, 애플리케이션 DTO | HTTP/SQL/파일 접근 구현, 프레임워크 | Domain |
| **Interface Adapter** | 컨트롤러, 프리젠터, 리포지토리 구현, 매퍼, 뷰모델 | 비즈니스 규칙 | Application, Domain |
| **Infrastructure** | ORM 설정, HTTP 클라이언트, 메시지 브로커, DI 컨테이너, 설정 로더 | 비즈니스 규칙 | 전 계층 (조립 지점) |

### 계층 배치 판단 기준

새 코드를 어디에 둘지 헷갈릴 때 다음 순서로 자문한다:

1. **"이 규칙은 이 서비스가 없어도 업무상 참인가?"** → Yes면 Domain
   - 예: "주문 총액은 항목 금액의 합이다" → Domain
2. **"이 흐름은 사용자의 의도 한 단위를 표현하는가?"** → Yes면 Application
   - 예: "주문을 생성하고 재고를 차감하고 알림을 보낸다" → Application
3. **"이건 외부 세계와 우리 모델을 번역하는가?"** → Yes면 Interface Adapter
   - 예: HTTP 요청 바디 → 유스케이스 입력 DTO 변환
4. **"이건 기술 선택의 결과물인가?"** → Yes면 Infrastructure

### 계층 수 조절

계층을 4개로 고정하지 않는다. **규모에 맞춰 접는다.**

| 프로젝트 성격 | 권장 계층 |
|-------------|----------|
| 단순 CRUD, 도메인 규칙 거의 없음 | Application + Infrastructure 2계층. Domain 강제 금지 |
| 도메인 규칙이 있는 일반 서비스 | Domain + Application + Adapter + Infra 4계층 |
| 복수 바운디드 컨텍스트, 대규모 | 4계층 + 컨텍스트별 모듈 분리 |

과도한 계층화는 원칙 준수가 아니라 **낭비**다. 계층을 줄이는 결정은
ADR로 기록하고 리뷰에서 확인한다.

## 3. SOLID 적용 기준

SOLID는 암기 대상이 아니라 **냄새를 감지하는 렌즈**다. 각 원칙마다
"위반의 관찰 가능한 증상"을 기준으로 판단한다.

| 원칙 | 위반 증상 (관찰 가능) | 조치 |
|------|---------------------|------|
| **SRP** | 한 파일/클래스가 서로 다른 이유로 자주 함께 수정된다. 커밋 히스토리에서 무관한 변경이 같은 파일에 몰린다 | 변경 이유(액터) 단위로 분리 |
| **OCP** | 새 유형을 추가할 때마다 기존 `switch`/`if-else` 체인을 수정한다 | 다형성 또는 전략 등록 테이블로 대체 |
| **LSP** | 하위 타입이 상위 타입 자리에서 예외를 던지거나 no-op으로 동작한다 | 상속 대신 합성. 인터페이스 분리 |
| **ISP** | 구현체가 인터페이스 메서드 절반을 `throw NotImplemented`로 채운다 | 인터페이스를 역할 단위로 쪼갠다 |
| **DIP** | 상위 모듈 파일 상단 import에 DB 드라이버/HTTP 클라이언트가 보인다 | 포트 인터페이스 선언 후 주입 |

**우선순위:** 실무에서 가장 자주 문제가 되는 것은 **SRP와 DIP**다.
설계 리뷰에서 이 둘을 먼저 확인하고, 나머지는 증상이 보일 때 적용한다.

## 4. 순수성 원칙

> **기본값은 순수 함수 / 순수 클래스다. 부수 효과는 예외이며, 예외는 가장자리로 밀어낸다.**

### 순수의 정의

- 같은 입력 → 항상 같은 출력
- 외부 상태를 읽거나 쓰지 않음 (전역 변수, 현재 시각, 난수, I/O, DB)
- 인자를 변형(mutate)하지 않음

### Functional Core, Imperative Shell

```
┌─────────────────────────────────────┐
│ Imperative Shell (얇게)              │  I/O, 시각, 난수, DB, 네트워크
│  ┌───────────────────────────────┐  │
│  │ Functional Core (두껍게)       │  │  결정 로직 전부. 순수.
│  │  입력 → 계산 → 결정 반환       │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

**설계 절차:**
1. 부수 효과가 필요한 지점을 식별한다 (시각, 난수, ID 생성, 저장, 전송)
2. 그 값들을 **함수 인자로 주입**받도록 시그니처를 바꾼다
3. 결정 로직은 순수 함수로 계산하고, **"무엇을 할지"를 데이터로 반환**한다
4. 셸이 그 데이터를 실행한다

```
# 나쁨 — 순수 로직과 부수 효과가 섞임
def process_order(order_id):
    order = db.find(order_id)            # I/O
    if order.total > 100000:
        order.discount = order.total*0.1 # 규칙
    db.save(order)                       # I/O
    mailer.send(order.email)             # I/O

# 좋음 — 결정은 순수, 실행은 셸
def decide_discount(order: Order) -> Decision:      # 순수. 단위 테스트 즉시 가능
    if order.total > 100_000:
        return Decision(discount=order.total * 0.1, notify=True)
    return Decision(discount=0, notify=False)

def process_order(order_id, db, mailer):            # 셸. 얇다
    order = db.find(order_id)
    decision = decide_discount(order)
    db.save(order.apply(decision))
    if decision.notify:
        mailer.send(order.email)
```

### 순수 클래스

클래스를 쓸 때의 기본형:
- 생성자에서 불변식을 검증하고, 이후 필드는 **불변(immutable)**
- 상태 변경 메서드는 `self`를 바꾸지 않고 **새 인스턴스를 반환**
- 정적 팩토리로 생성 의도를 명시 (`Order.draft()`, `Order.restore()`)

가변 상태가 정말 필요한 경우(성능 임계 경로, 대용량 버퍼)에만 예외를 두고,
그 이유를 코드 주석이 아니라 **ADR로 기록**한다.

## 5. 경계면 계약

경계면 불일치는 런타임 장애의 최대 원인이다 (`integration-qa` 스킬 참조).
설계 시점에 다음을 **문서화된 계약**으로 고정한다.

| 경계면 | 계약으로 고정할 것 |
|--------|------------------|
| API ↔ 클라이언트 | 응답 래핑 여부, 필드 네이밍 컨벤션, 에러 바디 형태, 상태 코드 의미 |
| 서비스 ↔ DB | 컬럼명 ↔ 도메인 필드명 매핑 표, null 허용 여부, 트랜잭션 경계 |
| 상태 머신 | 허용 전이 목록. 코드의 모든 상태 변경은 이 목록에 있어야 함 |
| 비동기 작업 | 즉시 응답(202)의 shape과 최종 결과의 shape을 **별개 타입**으로 정의 |
| 모듈 ↔ 모듈 | 공개 인터페이스 목록. 그 외는 내부 구현으로 간주 |

**네이밍 일관성 규칙:** 시스템 전체에서 하나의 개념은 하나의 이름을 갖는다.
DB가 `snake_case`, API가 `camelCase`라면 **변환 지점을 단 한 곳(매퍼)** 으로
강제하고, 그 매퍼에 대한 테스트를 반드시 작성한다.

## 6. 원칙을 굽히는 절차

원칙은 목적이 아니라 수단이다. 다음 상황에서는 굽힐 수 있다:

- 프로토타입/스파이크 — 폐기가 전제된 코드
- 성능 임계 경로 — 측정으로 입증된 병목
- 외부 프레임워크 강제 — 프레임워크가 특정 구조를 요구할 때
- 규모 대비 과설계 — 계층 축소 (2절 참조)

**단, 반드시 다음을 따른다:**
1. `docs/plan/adr/` 에 ADR을 작성한다 (무엇을, 왜, 대안, 되돌리는 조건)
2. 리뷰 게이트에서 사용자에게 보고한다
3. 되돌리는 조건(trigger)을 명시한다 — "트래픽 X 이하로 떨어지면 원복" 등

**암묵적 예외는 금지한다.** 기록되지 않은 원칙 위반은 리뷰에서 결함으로 처리한다.

## 7. 자동 검증 가능한 규칙 목록

`architecture-guard` 스킬이 이 목록을 검증 테스트로 구현한다.
프로젝트마다 적용 가능한 항목을 선택한다.

| # | 규칙 | 검증 방법 |
|---|------|----------|
| A1 | Domain 계층이 Application/Adapter/Infra를 import하지 않는다 | import 그래프 정적 분석 |
| A2 | Application 계층이 Infra 구체 타입을 import하지 않는다 | import 그래프 정적 분석 |
| A3 | Domain 계층에 프레임워크 어노테이션/데코레이터가 없다 | 소스 패턴 검색 |
| A4 | 계층 간 순환 의존이 없다 | 의존 그래프 사이클 검출 |
| A5 | 공개 유스케이스마다 대응 테스트가 존재한다 | 파일 매핑 검사 |
| A6 | Domain 테스트가 I/O 없이 실행된다 | 테스트 실행 시 네트워크/DB 모듈 로드 금지 |
| A7 | 상태 변경 코드가 전이 맵에 정의된 전이만 수행한다 | 전이 맵 ↔ 상태 변경 호출부 대조 |
| A8 | API 응답 타입과 클라이언트 소비 타입이 일치한다 | 계약 스키마 ↔ 양쪽 타입 대조 |
| A9 | 네이밍 변환이 지정된 매퍼에서만 일어난다 | 변환 함수 호출 위치 검사 |

**기본 선택은 A1~A4다.** 유효 설정의 architecture_rules와 미적용 근거를 따른다. 나머지는 해당 요소가
존재할 때 추가한다.
