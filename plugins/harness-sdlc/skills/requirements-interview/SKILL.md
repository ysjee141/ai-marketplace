# Requirements Interview — 요구사항 구체화와 PRD 작성

## 목적

사용자의 요구를 **구현 가능한 수준까지 구체화**하고 PRD로 문서화한다.
이후 모든 단계가 이 문서를 전제로 하므로, 여기서의 공백은 그대로 전파된다.

## 절차

### 1. 기존 정보 수집 (질문 전에)

질문하기 전에 이미 답이 있는 것을 찾는다. 아는 것을 묻는 것은 신뢰를 깎는다.

- `docs/` 하위 기존 문서, ADR
- README, 기존 코드의 유사 기능
- 사용자가 제공한 첨부 자료 (`_workspace/{slug}/00_input/`)

### 2. 공백 식별

`docs/template/prd.md`를 열어 채울 수 있는 섹션을 먼저 채운다.
**채우지 못한 섹션이 곧 질문 대상**이다.

### 3. 질문 설계

| 규칙 | 이유 |
|------|------|
| 한 라운드에 3~7개 | 하나씩 던지면 사용자가 지친다. 10개 넘으면 답변 품질이 떨어진다 |
| 답이 다른 답에 의존하면 다음 라운드로 | 순환 질문을 피한다 |
| 선택지를 제시한다 | 열린 질문보다 답하기 쉽고 답이 구체적이다 |
| 각 선택지에 트레이드오프를 붙인다 | 사용자가 정보에 근거해 결정할 수 있다 |
| 업계 관행상 자명한 것은 묻지 않는다 | 가정으로 기록하고 넘어간다 |

**질문 형식 예:**

```markdown
### Q2. 인증 방식

| 선택지 | 장점 | 단점 |
|--------|------|------|
| ① 세션 쿠키 | 즉시 무효화 가능, 구현 단순 | 서버 상태 필요, 확장 시 공유 저장소 |
| ② JWT | 서버 무상태, 확장 용이 | 즉시 무효화 곤란, 토큰 크기 |
| ③ OAuth 위임 | 비밀번호 관리 불필요 | 외부 의존, 초기 설정 복잡 |

권장: ① — 현재 규모에서 무효화 요구가 더 중요해 보입니다.
```

### 4. 질문 영역 체크리스트

**불명확한 것만** 묻는다. 이미 답이 있는 영역은 건너뛴다.

| 영역 | 확인할 것 | 놓치면 생기는 일 |
|------|----------|-----------------|
| 사용자·역할 | 누가 쓰는가, 역할별 권한 차이 | 권한 설계를 나중에 갈아엎는다 |
| 핵심 시나리오 | 성공 경로를 단계별로 서술 가능한가 | 화면·API가 실제 흐름과 어긋난다 |
| 데이터 | 무엇을 저장, 보존 기간, 개인정보 여부 | 스키마·규제 대응을 다시 한다 |
| 제약 | 기존 시스템, 스택, 규제, 기한 | 구현 후 못 쓴다는 것을 안다 |
| 성공 지표 | 무엇이 측정되면 성공인가 | 완료 판정이 불가능하다 |
| 실패·예외 | 실패 시 어떻게 되어야 하는가 | 에러 처리가 즉흥적이 된다 |
| 범위 제외 | 이번에 안 할 것 | 범위가 무한히 팽창한다 |
| 비기능 | 성능·가용성·보안·접근성 수준 | 아키텍처를 다시 짠다 |

### 5. 모호 표현 제거

다음 표현이 요구사항에 남아 있으면 **반드시 구체화한다.**

| 모호 표현 | 되물을 것 |
|----------|----------|
| "빠르게", "쾌적하게" | 응답 목표 시간은? 어떤 조건에서? |
| "많은 사용자" | 동시 몇 명? 일 몇 명? |
| "안전하게" | 어떤 위협을 막아야 하는가? |
| "사용하기 쉽게" | 어떤 조작이 몇 단계 안에 끝나야 하는가? |
| "기존과 비슷하게" | 어느 기존 것? 어느 부분이 같고 어느 부분이 다른가? |
| "나중에 확장 가능하게" | 어떤 확장을 예상하는가? 지금 대비할 범위는? |

### 6. PRD 작성

`docs/template/prd.md` 템플릿을 정확히 따른다.

**작성 규칙:**
- 결정된 것은 단정형으로 쓴다
- 사용자가 "알아서 해줘"라 한 항목은 **당신이 결정하고 §가정에 기록**한다.
  되묻지 않는다
- 여전히 결정되지 않은 항목은 §미결정에 남긴다. 삭제하거나 추측으로 채우지 않는다
- 각 요구사항에 ID를 붙인다 (`FR-1`, `NFR-1`) — 이후 추적성의 기반

| 파일 | 내용 |
|------|------|
| `_workspace/{slug}/01_planning/prd-draft.md` | PRD 본문 |

## 재실행 시

기존 `prd-draft.md`가 있으면:
1. 먼저 읽는다
2. 피드백·게이트 지적에 해당하는 **부분만** 수정한다. 전면 재작성하지 않는다
3. frontmatter의 `version`을 올리고 `updated`를 갱신한다
4. 변경된 요구사항 ID를 목록으로 보고한다 — 하위 단계 산출물에 영향을 준다

## 완료 판정

다음을 모두 만족해야 게이트 G1에 진입한다:

- [ ] 템플릿의 모든 필수 섹션이 채워졌다
- [ ] 성공 지표가 측정 가능하다
- [ ] 범위 밖이 명시되었다
- [ ] 모호 표현이 남아 있지 않다
- [ ] 미결정 항목이 미결정으로 표시되었다
- [ ] 각 요구사항에 ID가 있다
- [ ] 사용자가 PRD 내용을 확인했다

## 대화가 불가능한 환경일 때

배치 실행 등으로 사용자 응답을 받을 수 없으면:
1. 답을 지어내지 않는다
2. 알 수 있는 범위까지 PRD를 작성한다
3. 미결정 항목을 **전부 나열**하고 각각의 영향을 명시한다
4. "이 PRD는 미결정 N건을 포함하며, 확정 없이 다음 단계로 진행하면
   재작업 위험이 있음"을 서두에 기록한다
