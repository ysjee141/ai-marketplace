# Tech Spec Authoring — 기술 명세 및 ADR 작성

## 목적

요구사항을 **구현 가능한 기술 명세**로 번역하고, 그 과정의 갈림길을 ADR로 드러낸다.

## 원칙

- **모든 PRD 요구사항에 대응 명세가 있어야 한다.** 추적 매트릭스로 증명한다.
- **결정을 명세 안에 묻지 않는다.** "Redis를 사용한다" 한 줄로는 왜 그런지
  아무도 알 수 없고, 6개월 뒤 누군가 아무 근거 없이 뒤집는다.
- **구현 방법이 아니라 계약을 쓴다.** "for문을 돌며 검증한다"가 아니라
  "입력 X가 조건 Y를 만족하지 않으면 오류 Z를 반환한다".
- **분석 결과의 리스크를 명세에 반영한다.** 심각도 높음 리스크에는 대응 방안이 있어야 한다.
- 아키텍처 원칙을 위반하는 명세를 쓰지 않는다. 불가피하면 그것 자체를 ADR로 만든다.

## 절차

### 1. 입력 정리

| 입력 | 추출할 것 |
|------|----------|
| PRD | 요구사항 ID 목록 (FR-*, NFR-*), 가정, 미결정 |
| 기획분석 | `반증됨`·`재검토 필요` 판정 항목 → 명세에 반영 필요 |
| 개발분석 | 리스크 목록, 기존 관례, 재사용 자산 |

**분석에서 `반증됨` 판정이 나온 요구사항은 명세를 쓰기 전에 해결한다.**
PRD 수정을 요청하거나, 사용자에게 판단을 구한다.

### 2. Spec 구조 채우기

`docs/template/tech-spec.md` 템플릿을 따른다. 필수 구성:

| 섹션 | 내용 |
|------|------|
| 개요 | 무엇을 만드는가 (3줄 이내) |
| 범위 | 포함 / 제외 |
| 기술 스택 | 사용 기술과 버전. 신규 도입은 ADR 참조 |
| 시스템 구성 | 컴포넌트와 책임 |
| 기능 명세 | 요구사항 ID별 동작 계약 |
| 데이터 명세 | 저장 대상, 생명주기, 정합성 요구 |
| 인터페이스 명세 | 외부 노출 계약(개요 수준. 상세는 설계 단계) |
| 비기능 명세 | 성능·가용성·보안·접근성의 **측정 가능한** 목표 |
| 에러 정책 | 에러 분류, 사용자 노출 수준, 로깅 방침 |
| 리스크 대응 | 분석 리스크별 대응 |
| **추적 매트릭스** | PRD 요구 ↔ Spec 섹션 ↔ ADR |

### 3. 기능 명세 작성 방식

각 요구사항을 **입력 → 조건 → 결과** 계약으로 쓴다.

```markdown
### FR-3 로그인

| 항목 | 내용 |
|------|------|
| 입력 | 이메일, 비밀번호 |
| 사전 조건 | 계정이 존재하고 활성 상태 |
| 성공 | 세션 발급. 만료 시각 포함 반환 |
| 실패 — 자격 불일치 | `INVALID_CREDENTIALS`. **어느 쪽이 틀렸는지 구분하지 않는다** (계정 열거 방지) |
| 실패 — 비활성 계정 | `ACCOUNT_DISABLED` |
| 실패 — 시도 초과 | `TOO_MANY_ATTEMPTS`. 5회/5분 |
| 부수 효과 | 로그인 감사 로그 기록 |
```

"어느 쪽이 틀렸는지 구분하지 않는다"처럼 **의도적 결정에는 이유를 붙인다.**
이유가 없으면 나중에 "친절하게" 바뀐다.

### 4. ADR 분리

다음 중 하나라도 해당하면 ADR로 만든다:

| 기준 | 예 |
|------|-----|
| 대안이 2개 이상이고 트레이드오프가 있다 | 세션 저장소 선택 |
| 되돌리는 비용이 크다 | DB 엔진, 통신 프로토콜 |
| 아키텍처 원칙의 예외를 만든다 | 계층 축소, 가변 상태 도입 |
| 외부 의존을 새로 도입한다 | 신규 라이브러리·SaaS |
| 팀 기존 관례와 다르다 | 새 테스트 프레임워크 |
| 보안·개인정보 처리 방식 | 암호화 범위, 로그 마스킹 |

**ADR로 만들지 않는 것:** 관례상 자명한 선택, 되돌리기 쉬운 국소 결정,
이미 기존 ADR로 결정된 사항(참조만).

### 5. ADR 작성

`docs/template/adr.md` 템플릿. 번호는 `docs/plan/adr/`의 기존 최대값 +1
(저장소 전역 증가).

필수 요소와 작성 요령:

| 요소 | 요령 |
|------|------|
| 맥락 | 왜 지금 이 결정이 필요한가. 제약은 무엇인가 |
| 결정 | 단정형 한 문장 + 상세 |
| 고려한 대안 | **각각의 장단점.** 대안 없이 결정만 있으면 ADR이 아니다 |
| 결과 | 긍정적 결과와 **부정적 결과 모두**. 부정이 없으면 검토가 부족한 것 |
| **되돌리는 조건** | 이 결정이 언제 무효가 되는가 |

**되돌리는 조건이 가장 자주 빠지고, 가장 중요하다.** 적어두지 않으면
아무도 재검토하지 않고, 결정은 영원히 굳는다.

예: *"동시 접속 5천을 넘거나, 세션 데이터가 4KB를 초과하면 재검토"*

### 6. 사용자 승인

Spec 완성 후 **ADR 목록을 보고하고 승인을 받는다.** 승인 없이 설계로 넘기지 않는다.

```markdown
## ADR 승인 요청

| ADR | 결정 | 주요 대안 | 부정적 결과 | 되돌리는 조건 |
|-----|------|----------|-----------|-------------|
| ADR-0003 | 세션을 Redis에 저장 | DB(느림), JWT(무효화 곤란) | Redis 운영 부담 추가 | 동시 접속 5천 초과 |

승인하시겠습니까? (전체 승인 / 번호별 재검토)
```

## 추적 매트릭스

Spec에 반드시 포함한다. G3 판정의 핵심 근거다.

| PRD 요구 | Spec 섹션 | 관련 ADR | 비고 |
|---------|----------|---------|------|
| FR-1 회원가입 | §4.1 | - | - |
| FR-3 로그인 | §4.3 | ADR-0003 | - |
| NFR-2 응답 200ms | §7 성능 | ADR-0005 | 캐시 계층 도입 |
| FR-7 SNS 로그인 | - | - | **범위 제외** (PRD §범위밖) |

대응이 없는 요구사항은 **누락**이거나 **명시적 제외**다. 둘 다 표에 드러나야 한다.

## 재실행 시

기존 Spec을 읽고 지적 항목만 수정한다. **ADR은 수정하지 않는다** —
결정을 뒤집을 때는 새 ADR을 만들고 이전 것을 `status: superseded`로 바꾼다.
ADR의 불변성이 결정 이력의 신뢰성을 만든다.

## 완료 판정

- [ ] 추적 매트릭스가 있고 PRD 요구가 모두 대응된다
- [ ] 기능 명세가 입력→조건→결과 계약으로 작성되었다
- [ ] 비기능 목표가 측정 가능하다
- [ ] 대안이 있는 선택이 모두 ADR로 분리되었다
- [ ] 각 ADR에 대안·부정적 결과·되돌리는 조건이 있다
- [ ] 심각도 높음 리스크에 대응이 있다
- [ ] **ADR이 사용자에게 보고되고 승인되었다**
