# Codebase Analysis — 개발분석 및 리스크 평가

## 목적

구현 관점에서 **무엇을 건드려야 하는지, 무엇이 깨질 수 있는지, 무엇이 예상보다
어려운지**를 밝힌다.

## 원칙

- **"어디를 고쳐야 하는가"까지 답한다.** "인증 모듈이 관련 있다"는 분석이 아니다.
  `src/auth/session.py:40-88`처럼 짚는다.
- **읽지 않은 코드를 단정하지 않는다.** 추정이면 추정이라 표기한다.
- **기존 관례와 하네스 원칙의 충돌을 리스크로 올린다.** 임의로 한쪽을 택하지 않는다.
- **테스트 현황을 반드시 확인한다.** 테스트 없는 영역의 변경은 그 자체로 높은 리스크다.
- 파일을 수정하지 않는다.

## 절차

### 1. 진입점 찾기

요구사항의 키워드로 코드베이스를 훑어 **관련 영역의 경계**를 먼저 정한다.
전수 분석을 시도하지 않는다 — 시간이 무한하지 않고, 대부분은 무관하다.

탐색 순서: 도메인 용어 검색 → 해당 모듈 → 그 모듈을 참조하는 호출부 →
그 모듈이 의존하는 것.

### 2. 분석 체크리스트

| 영역 | 확인할 것 | 산출 형태 |
|------|----------|----------|
| 기술 스택 | 언어·프레임워크·라이브러리와 **버전** | 목록 |
| 계층 구조 | 현재 계층 분리 수준, 의존 방향 위반 | 구조 요약 + 위반 목록 |
| 영향 범위 | 변경 필요 파일·모듈, 그것을 참조하는 호출부 | 파일:라인 목록 |
| 경계면 | 건드리는 API·DB 스키마·이벤트 계약 | 경계면 목록 |
| 데이터 | 마이그레이션 필요 여부, 기존 데이터 호환성 | 판정 + 근거 |
| 테스트 | 영향 영역의 테스트 존재·커버리지·실행 방법 | 현황표 + 실행 명령 |
| 빌드/실행 | 빌드·테스트·기동 명령, 전제 조건 | 명령 목록 |
| 기술 부채 | 이번 작업을 방해하는 기존 부채 | 리스크로 등록 |

**빌드·테스트 명령을 실제로 실행해 확인한다.** 문서에 적힌 명령이 실제로
동작하지 않는 경우는 흔하며, 그 자체가 리스크다.

### 3. 영향 범위 산출

변경의 파급을 3단계로 구분한다:

| 단계 | 정의 | 예 |
|------|------|-----|
| 직접 | 이 파일을 수정해야 한다 | `src/auth/session.py` |
| 간접 | 직접 대상을 호출하므로 영향받는다 | `src/api/login.py:22` |
| 잠재 | 같은 데이터·계약을 공유하여 영향 가능성 | 세션 테이블을 읽는 배치 작업 |

**잠재 영역을 빠뜨리면 배포 후에 발견된다.** 데이터·계약을 공유하는 곳을
반드시 검색한다.

### 4. 리스크 평가

| # | 리스크 | 심각도 | 발생 가능성 | 근거 | 완화책 |
|---|--------|--------|-----------|------|--------|
| R1 | 세션 저장 방식 변경 시 기존 로그인 전부 만료 | 높음 | 확실 | `src/auth/session.py:40` 단일 저장소 가정 | 이중 읽기 기간 후 전환 |

심각도: `높음`(장애·데이터 손실·보안) | `중간`(기능 저하·재작업) | `낮음`(불편)
발생 가능성: `확실` | `높음` | `보통` | `낮음`

**리스크 발굴 질문** — 이 목록을 순회하며 자문한다:

- 이 변경으로 **기존 사용자의 무엇이 깨지는가?** (세션·저장 데이터·URL·API)
- 배포 중간 상태(구/신 버전 공존)에서 무엇이 깨지는가?
- 되돌려야 할 때 되돌릴 수 있는가?
- 이 영역에 테스트가 없다면, 회귀를 무엇으로 잡는가?
- 성능·부하 특성이 바뀌는가?
- 외부 시스템·계약에 영향이 있는가?
- 개인정보·권한 경계가 이동하는가?

**심각도 높음 + 발생 가능성 확실/높음** 조합은 계획 단계에서 **별도 Task로
다뤄져야 한다**고 산출물에 명시한다.

### 5. 관례 학습

이후 구현 에이전트가 따라야 할 기존 관례를 정리한다:

| 항목 | 관례 | 근거 |
|------|------|------|
| 디렉토리 구조 | 기능별 수직 분할 | `src/features/*` |
| 명명 | 파일 snake_case, 클래스 PascalCase | 전반 |
| 에러 처리 | 도메인 예외 → HTTP 매핑 계층 존재 | `src/api/errors.py` |
| 테스트 | pytest, `tests/` 미러 구조 | `tests/` |

하네스 원칙과 충돌하는 관례가 있으면 **리스크로 등록하고 판단을 요청한다.**

## 신규 프로젝트일 때

코드베이스가 비어 있으면 분석 대상을 전환한다:
1. "신규 프로젝트 — 기존 제약 없음" 명시
2. 기술 스택 선택 시 고려사항으로 분석 범위를 바꾼다
3. 리스크는 "선택의 리스크"로 평가한다 (팀 숙련도, 생태계 성숙도, 운영 부담)

## 재실행 시

기존 impact 파일을 읽고 지적된 누락 영역만 추가 분석한다.
이미 확인된 파일은 재탐색하지 않는다.

## 완료 판정

- [ ] 영향 범위가 직접/간접/잠재로 구분되어 파일 수준으로 특정되었다
- [ ] 리스크가 심각도·발생 가능성·완화책과 함께 목록화되었다
- [ ] 테스트 현황과 실행 명령이 확인되었다 (실제 실행 확인)
- [ ] 기존 관례가 정리되었다
- [ ] 원칙 충돌이 있으면 리스크로 등록되었다
- [ ] **미분석 영역이 명시되었다** (전부 봤다고 주장하지 않았다)
