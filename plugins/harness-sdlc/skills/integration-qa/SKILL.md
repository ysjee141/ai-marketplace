# Integration QA — 통합 정합성 검증

## 목적

개별 모듈이 각각 올바른데 **연결 지점에서 계약이 어긋나는 결함**을 잡는다.
빌드·타입 검사·단위 테스트를 모두 통과하고도 런타임에 터지는 것들이다.

## 왜 정적 검사로 안 잡히는가

| 원인 | 설명 |
|------|------|
| 제네릭·캐스팅 | `fetchJson<Item[]>()` — 런타임 응답이 `{items: [...]}`여도 컴파일 통과 |
| `any` / 동적 타입 | 타입 정보가 소실되어 검사 대상에서 빠진다 |
| 문자열 경로·채널 | `href="/projects/1"`가 실존하는지 컴파일러는 모른다 |
| 계층 간 독립 검증 | 양쪽이 각각 "정상"이면 개별 테스트는 통과한다 |
| 빌드 성공 = 정상 아님 | 빌드는 구조만 본다. 값의 shape은 보지 않는다 |

**"존재 확인"과 "연결 확인"은 전혀 다른 검증이다.**
"API가 있는가?"가 아니라 "API의 응답이 호출측의 기대와 일치하는가?"를 묻는다.

## 핵심 방법: 양쪽 동시 읽기

**한쪽만 읽으면 경계면 결함을 절대 잡을 수 없다.**

| 검증 대상 | 왼쪽 (생산자) | 오른쪽 (소비자) |
|----------|-------------|---------------|
| API 응답 shape | 서버 응답 직렬화 코드 | 클라이언트 fetch·타입 파라미터 |
| 라우팅 | 페이지·라우트 정의 파일 경로 | `href`, `router.push`, `redirect` 값 |
| 상태 전이 | 전이 맵 / 설계 다이어그램 | 실제 status 갱신 코드 |
| DB → 도메인 | 마이그레이션 컬럼명 | 매퍼·엔티티 필드명 |
| IPC (데스크탑) | 메인 프로세스 핸들러 | 렌더러 호출부 |
| 이벤트 | 발행 코드의 페이로드 | 구독 코드의 기대 shape |
| 환경 변수 | 설정 정의·문서 | 실제 참조 코드 |

## 검증 절차

### 1. 경계면 목록 작성

먼저 검증 대상 경계면을 전부 나열한다. 목록 없이 시작하면 빠뜨린다.

```markdown
| # | 경계면 | 생산자 | 소비자 | 우선순위 |
|---|--------|--------|--------|---------|
| 1 | POST /api/sessions | src/api/sessions.py | src/hooks/useLogin.ts | 높음 |
| 2 | orders 상태 전이 | src/domain/order/transitions.py | src/application/order/*.py | 높음 |
```

우선순위: 사용자 주요 경로 > 데이터 변경 > 조회 > 관리 기능

### 2. API ↔ 소비자 교차 검증

```
1. 서버 응답 직렬화 코드에서 실제 반환 객체의 shape을 추출
2. 소비자의 타입 파라미터·구조 분해를 확인
3. 래핑 여부 대조 — 생산자가 { data: T } 면 소비자가 .data를 꺼내는가
4. 필드명 대조 — camelCase/snake_case 일치 여부
5. null·옵셔널 처리 대조
6. 에러 응답 형태 대조
```

**특히 주의:**
- 목록 API가 `{items, total}`인데 소비자가 배열로 기대
- 즉시 응답(202)의 shape과 최종 결과 shape 혼동
- 페이지네이션 메타 필드명 불일치

### 3. 엔드포인트 ↔ 소비자 1:1 매핑

```
1. 모든 API 엔드포인트 목록 추출 (메서드 + 경로)
2. 모든 클라이언트 호출 URL 목록 추출
3. 대응 없는 엔드포인트 → "미사용" 플래그
4. 대응 없는 호출 → "존재하지 않는 엔드포인트" (BLOCKER)
5. "미사용"이 의도적인지(관리 API) 누락인지 판정
```

**"미사용 엔드포인트"는 대개 소비자 구현 누락**이다.
설계에 있는데 호출되지 않으면 그 기능은 동작하지 않는다.

### 4. 라우팅 정합성

```
1. 페이지·라우트 정의에서 실제 URL 패턴 추출
   - 라우트 그룹은 URL에서 제거됨을 반영
   - 동적 세그먼트 식별
2. 코드 내 모든 href / router.push / redirect 값 수집
3. 각 링크가 실존 경로와 매칭되는지 대조
```

접두사 누락(`/projects/1` vs `/dashboard/projects/1`)이 가장 흔하다.

### 5. 상태 전이 완전성

```
1. 전이 맵(설계 또는 코드 상수)에서 허용 전이 목록 추출
2. 코드의 모든 status 갱신 지점 검색
3. 무단 전이 — 코드에 있으나 맵에 없음 → BLOCKER
4. 죽은 전이 — 맵에 있으나 코드에 없음 → BLOCKER
5. 소비자의 상태 분기(if status === "X")에서 X가 도달 가능한지 확인
```

**죽은 전이가 특히 위험하다.** 중간 상태에서 최종 상태로 가는 전이가
구현되지 않으면 "영원히 로딩 중"인 화면이 된다.

### 6. DB ↔ 도메인 매핑

```
1. 마이그레이션에서 컬럼명·타입·null 허용 추출
2. 매퍼·엔티티의 필드명·타입 추출
3. 설계서의 매핑 표와 3자 대조
4. 변환이 매퍼 외부에서 일어나는지 확인 (A9 위반)
```

## 판정과 리포트

### 정본 판정

불일치 발견 시 **어느 쪽이 맞는지 판정한다.**
"양쪽이 알아서 맞추세요"로 넘기지 않는다.

| 판정 근거 | 우선순위 |
|----------|---------|
| API 계약 문서 | 1 |
| 설계서 | 2 |
| Tech Spec | 3 |
| 근거 없음 → 계약 모호성 자체가 결함(MAJOR) | - |

### 리포트 형식

`_workspace/{slug}/05_implement/qa-report-r{N}.md`

| # | 심각도 | 경계면 | 생산자 | 소비자 | 불일치 | 정본 | 담당 |
|---|--------|--------|--------|--------|--------|------|------|
| 1 | BLOCKER | API→웹 | `api/sessions.py:42` 가 `{data:{...}}` 반환 | `hooks/useSession.ts:15` 가 평면 객체 기대 | 래핑 누락 | 계약 §2 | frontend-web |
| 2 | MAJOR | 전이맵→코드 | 설계 §5 `paid→shipped` | 갱신 코드 없음 | 죽은 전이 | 설계 | backend |

**심각도:**

| 심각도 | 기준 |
|--------|------|
| BLOCKER | 런타임 오류·기능 미동작이 확실 |
| MAJOR | 특정 조건에서 오류. 데이터 불일치 |
| MINOR | 동작하나 규약 위반 (네이밍, 미사용 코드) |

### 반드시 구분할 것

리포트에 **통과 / 실패 / 미검증**을 구분한다.
검증하지 않은 것을 통과로 적으면 QA가 무의미해진다.

## 점진적 실행

**전체 완성을 기다리지 않는다.** 각 모듈이 완성될 때마다 즉시 해당 경계면을
검증한다. 이유:

- 결함이 누적되면 수정 비용이 급증한다
- 초기 경계면 불일치가 후속 모듈로 전파된다 (잘못된 shape을 전제로 다음 코드가 쌓임)
- 담당 에이전트가 컨텍스트를 잃기 전에 고치는 편이 정확하다

**권장 시점:** API 하나가 완성되면 즉시 해당 API + 소비자 교차 검증.

## 통신 규약

- 결함 발견 즉시 담당 에이전트에게 **`파일:라인 + 불일치 + 정본 + 수정 방법`** 전달
- **경계면 결함은 양쪽 에이전트 모두에게 알린다** — 한쪽만 고치면 다시 어긋난다
- 계약 해석이 모호하면 `network-engineer`에게 정본 판정을 요청한다
- 명백한 오타 수준은 직접 고치고 보고한다. 그 외는 담당에게 반환한다

## 에러 핸들링

| 상황 | 대응 |
|------|------|
| 설계서·계약 문서 없음 | **"검증 불가"로 보고.** 코드만 보고 정상이라 판정하지 않는다 |
| 계약이 모호 | 모호성 자체를 MAJOR 결함으로 기록, `architect`에게 명확화 요청 |
| 대상 코드가 방대 | BLOCKER 위험 순으로 검증. **미검증 경계면 명시** |
| 실행 검증 불가 | 정적 교차 비교만 수행하고 한계를 명시 |
