# Review Gate — 리뷰 게이트 판정

## 목적

각 단계 산출물을 검증하여 **결함이 하위 단계로 전파되는 것을 막는다.**
통과시킨 결함의 수정 비용은 단계마다 배로 늘어난다.

## 판정 독립성

**생성자와 리뷰어를 분리한다.** 자기 산출물을 자기가 판정하면 관대해진다.

단일 에이전트 환경에서는 다음으로 독립성을 근사한다
(`harness/adapters/generic-agent.md` 3절):

1. 리뷰는 **별도 턴**에서 수행한다. 생성 직후 같은 응답에서 판정하지 않는다
2. **산출물 파일만 읽는다.** 생성 과정의 추론을 참조하지 않는다
3. 체크리스트를 **항목별로 명시 판정**한다
4. **지적 사항 표를 먼저 작성하고, 그 다음에 판정을 선언한다** —
   결론을 먼저 정하고 근거를 맞추는 순서를 피한다

## 원칙

- **"전반적으로 양호"는 판정이 아니다.** 항목별로 판정한다
- **결함이 없으면 통과시킨다.** 흠을 만들어내지 않는다. MINOR만 있으면 통과다
- **모호성을 결함으로 취급한다.** 읽는 사람에 따라 다르게 해석될 문장은
  이후 단계에서 반드시 어긋난다
- **기준 문서 없이 리뷰하지 않는다.** 개인 취향이 기준이 되면 리뷰는 소음이 된다
- **추적성을 확인한다.** 상위 문서의 항목이 하위에 반영되었는지, 하위에
  상위에 없는 내용이 슬쩍 들어오지 않았는지

## 게이트 구성

| 게이트 | 시점 | 리뷰어 | 대상 |
|--------|------|--------|------|
| G1 | 기획 후 | doc-reviewer | PRD |
| G2 | 분석 후 | doc-reviewer | 기획분석 + 개발분석 |
| G3 | 계획 후 | doc-reviewer | Tech Spec, ADR, WBS, Task |
| G4 | 설계 후 | doc-reviewer | 설계서, 경계면 계약, 다이어그램 |
| G5 | 구현·테스트 후 | code-reviewer + qa-inspector | 코드, 테스트, QA 리포트 |
| G6 | 최종 | doc-reviewer + code-reviewer | 전 단계 일관성 |

**각 게이트의 상세 체크리스트는 리뷰어 에이전트 정의에 있다:**
`.claude/agents/doc-reviewer.md`, `.claude/agents/code-reviewer.md`

## 심각도와 판정 규칙

| 심각도 | 정의 | 판정 영향 |
|--------|------|----------|
| **BLOCKER** | 이후 단계를 잘못된 전제 위에 쌓게 만든다 | **1건 → REJECT** |
| **MAJOR** | 재작업 비용이 크지만 진행은 가능 | **3건 이상 → REJECT** |
| **MINOR** | 개선 권고 | 판정 영향 없음. 기록만 |

### 심각도 판정 요령

*"이 항목을 고치지 않고 다음 단계로 가면 어떻게 되는가?"*

| 답 | 심각도 |
|----|--------|
| 다음 단계 산출물 전체를 다시 만들어야 한다 | BLOCKER |
| 일부를 다시 만들어야 한다 | MAJOR |
| 나중에 고쳐도 비용이 같다 | MINOR |

## 롤백 대상 판정

REJECT 시 **결함이 발생한 단계**로 돌아간다. 직전 단계가 아닐 수 있다.

| 지적의 성격 | 롤백 대상 |
|-----------|----------|
| 요구사항 자체가 모호·누락 | 01 기획 |
| 근거·리스크 조사 부족 | 02 분석 |
| 기술 선택·일정·Task 분해 오류 | 03 계획 |
| 계층 구조·경계면 계약 오류 | 04 설계 |
| 설계는 맞으나 코드가 어긋남 | 05 구현 |
| 테스트 부족·실패 | 05 구현 (테스트도 구현의 일부) |

**예:** G4(설계 리뷰)에서 "에러 정책이 정의되지 않아 경계면 계약을 확정할 수 없음"이
나오면, 이는 설계자의 잘못이 아니라 **Tech Spec의 누락**이다 → 03으로 롤백.

## 판정 파일 형식

`_workspace/{slug}/99_gate/gate-{stage}-r{N}.md`
템플릿: `docs/template/review.md`

```markdown
# 게이트 판정: {stage} (라운드 {N})

**대상**: `_workspace/{slug}/04_design/design.md`
**리뷰어**: doc-reviewer
**일시**: 2026-08-14 15:40

## 체크리스트 판정

| 항목 | 판정 | 비고 |
|------|------|------|
| 계층 구조와 의존 방향 명시 | 충족 | - |
| 경계면 계약 확정 | **미충족** | 에러 바디 형태 미정의 |
| 다이어그램 4종 | 부분 충족 | 상태 전이 다이어그램 없음 |
| ... | | |

## 지적 사항

| # | 심각도 | 위치 | 내용 | 조치 요구 |
|---|--------|------|------|----------|
| 1 | BLOCKER | design.md §6 | 에러 바디 형태가 정의되지 않음 — 소비자 구현 불가 | `{code,message,details?}` 형태와 code 목록 확정 |
| 2 | MAJOR | design.md §7 | 상태 전이 다이어그램 부재 | stateDiagram-v2 추가, 전이 맵과 일치 확인 |
| 3 | MINOR | design.md §3 | 용어 혼용 ("세션"/"토큰") | 용어집 기준으로 통일 |

## 판정

**REJECT** — BLOCKER 1건
**롤백 대상**: 04 설계
```

**지적에는 반드시 `위치 + 내용 + 조치 요구`가 있어야 한다.**
"이상함"은 지적이 아니다. 무엇을 어떻게 고쳐야 하는지 적는다.

## 재시도 한계

**같은 게이트에서 3회 연속 REJECT되면 자동 재작업을 중단한다.**

반복 반려는 다음 중 하나를 뜻하며, 재작업을 계속해도 해결되지 않는다:
- 상위 단계(요구사항·설계)의 결함
- 판정 기준이 비현실적
- 정보가 부족하여 애초에 작성 불가

사용자 보고 형식:

```markdown
게이트 {stage}가 3회 반려되었습니다.

- 반복 지적: {가장 자주 나온 지적}
- 추정 원인: {상위 단계 결함 | 기준 과도 | 정보 부족}

선택지:
1. {상위 단계}로 롤백하여 근본 원인 수정
2. 해당 지적을 예외로 승인하고 진행 (ADR 기록)
3. 판정 기준 조정
```

## 재리뷰 시

- 이전 라운드의 지적 사항을 먼저 읽고, **각각이 해소되었는지 확인**한다
- 해소되지 않은 항목은 심각도를 유지한다 (완화하지 않는다)
- 새 라운드 번호로 파일을 만든다 (`r1`, `r2` — 누적 보존)
- 이전에 지적하지 않았던 새 결함도 발견하면 지적한다.
  단, 같은 문서에서 라운드마다 새 결함이 계속 나오면 **첫 리뷰가 부실했던 것**이므로
  전면 재검토한다

## 에러 핸들링

| 상황 | 대응 |
|------|------|
| 산출물 없음 | 판정 불가로 보고. **통과시키지 않는다** |
| 상위 문서 없어 추적성 확인 불가 | 해당 항목만 "검증 불가"로 표기, 나머지 판정 |
| 판정 기준이 프로젝트에 부적합 | "해당 없음"으로 표기하고 사유 기록. 무시하지 않는다 |
| 리뷰 범위가 방대 | BLOCKER 위험이 높은 영역 우선. **미리뷰 영역 명시** |

## 완료 판정

- [ ] 체크리스트를 항목별로 명시 판정했다
- [ ] 지적 사항 표를 판정 선언보다 먼저 작성했다
- [ ] 각 지적에 위치·내용·조치 요구가 있다
- [ ] 심각도가 기준에 따라 부여되었다
- [ ] REJECT면 롤백 대상 단계가 지정되었다
- [ ] 판정 파일이 `99_gate/`에 저장되었다
