# Implementation Playbook — 구현 공통 절차

영역별 세부 지침은 `references/`에서 **필요한 것만** 로드한다.
공통 원칙은 이 문서에 있다.

| 담당 영역 | 로드할 reference |
|----------|-----------------|
| 웹 프론트엔드 | `references/frontend-web.md` |
| 모바일 앱 | `references/frontend-app.md` |
| 데스크탑 앱 | `references/frontend-desktop.md` |
| 백엔드 | `references/backend.md` |
| 데이터베이스 | `references/database.md` |
| 네트워크·통신 계약 | `references/network.md` |

## 공통 원칙

### 1. 설계서가 정본이다

- 설계서의 시그니처·이름·구조를 **그대로** 쓴다. 더 나은 이름이 떠올라도
  임의로 바꾸지 않는다 — 다른 에이전트가 그 이름으로 소비한다
- 변경이 필요하면 `architect`에게 요청한다. 혼자 바꾸면 경계면이 어긋난다
- 설계서로 구현이 불가능한 지점을 발견하면 **멈추고 보고**한다

### 2. 기존 관례를 따른다

새 프로젝트가 아니라면 기존 코드가 스타일의 정본이다.
디렉토리 구조·명명·에러 처리·테스트 배치를 먼저 읽고 맞춘다.

**하네스 원칙과 기존 관례가 충돌하면 구현을 멈추고 보고한다.**
혼자 판단해 스타일을 바꾸지 않는다.

### 3. 순수성을 기본값으로

`harness/principles/architecture.md` 4절.

- 결정 로직은 순수 함수로. 시각·난수·ID·I/O는 **인자로 주입**받는다
- 부수 효과는 얇은 셸에 국한한다
- 불변 객체가 기본. 가변이 필요하면 이유가 있어야 한다

이것이 테스트 가능성의 전부다. 순수하지 않은 코드는 테스트하기 어렵고,
테스트하기 어려운 코드는 결국 테스트되지 않는다.

### 4. 테스트 없는 코드를 남기지 않는다

- **같은 Task, 같은 PR 안에** 테스트가 있어야 한다
- "테스트는 다음 PR에서"는 허용되지 않는다
- 상세 기준은 `harness/principles/testing.md`

### 5. Task 범위를 지킨다

- Task 명세의 **범위 밖** 항목을 건드리지 않는다
- 요청받지 않은 리팩터링을 하지 않는다. 발견한 문제는 보고하고 Task로 만든다
- 범위를 벗어나는 변경이 필요하면 범위를 넓히지 말고 **새 Task를 요청**한다

### 6. 경계면을 임의로 해석하지 않는다

경계면 불일치는 런타임 장애의 최대 원인이다.

- API 응답 shape은 `api-contract.md`가 정본. 래핑 여부를 반드시 확인한다
- 계약과 실제 구현이 다르면 **양쪽에 알린다.** 한쪽에서 조용히 맞추지 않는다
- 계약에 없는 것이 필요하면 `network-engineer`에게 요청한다

## 구현 순서 (수직 슬라이스)

Task 하나를 완성하는 표준 순서:

| 순서 | 작업 | 산출 |
|------|------|------|
| 1 | 설계서·Task 명세·기존 코드 읽기 | 컨텍스트 |
| 2 | 도메인 요소 구현 + 불변식 테스트 | 값 객체·엔티티 |
| 3 | 포트 인터페이스 선언 | Application 계층 |
| 4 | 유스케이스 구현 + Fake 포트 테스트 | 응용 로직 |
| 5 | 어댑터 구현 + 통합/계약 테스트 | 리포지토리·컨트롤러 |
| 6 | 조립 (DI 연결) | Infrastructure |
| 7 | 아키텍처 검증 규칙 추가 (새 계층 도입 시) | 검증 테스트 |
| 8 | 구현 노트 작성 | `05_implement/impl-notes-*.md` |

**2~5를 한 Task 안에서 완성**하면 머지 시점에 동작하는 단위가 된다.
계층별로 쪼개 여러 Task로 나누면 마지막까지 아무것도 동작하지 않는다.

## 구현 노트

각 에이전트는 `_workspace/{slug}/05_implement/impl-notes-{영역}.md`를 작성한다.

| 항목 | 내용 |
|------|------|
| 설계와 달라진 점 | 무엇을, 왜. 승인 여부 |
| 확정한 계약 | 실제 응답 예시, 컬럼명, IPC 채널 등 |
| 발견한 문제 | 해결한 것과 남은 것 |
| 후속 필요 사항 | 다음 Task로 넘길 것 |
| 미구현·목(mock) 사용 | **반드시 명시.** 실제 연동 확인이 필요한 지점 |

**목을 쓰고 명시하지 않는 것이 가장 위험하다.** 통합 시점에 발견된다.

## 코드 품질 기준

| 항목 | 기준 |
|------|------|
| 함수 길이 | 화면 한 눈에 들어오는 정도. 넘으면 이름 붙일 수 있는 단위로 추출 |
| 중첩 깊이 | 3단계 초과 시 조기 반환·추출로 평탄화 |
| 매개변수 | 4개 초과 시 객체로 묶기 검토 |
| 주석 | "무엇"이 아니라 **"왜"**. 코드가 말하는 것을 반복하지 않는다 |
| 명명 | 용어집·설계서와 일치. 축약어는 도메인 표준만 |
| 에러 | 삼키지 않는다. 잡았으면 변환하거나 로깅하고 전파한다 |
| 매직 넘버 | 이름 있는 상수로. 단, 자명한 0/1은 예외 |

## 보안 기본

영역과 무관하게 지킨다:

- 비밀정보를 코드·설정 파일·로그에 넣지 않는다
- 사용자 입력을 쿼리·명령·경로에 그대로 넣지 않는다
- 권한 검사를 각 진입점에서 수행한다 (클라이언트 검사에 의존하지 않는다)
- 에러 메시지로 내부 구조를 노출하지 않는다
- 인증 실패 시 어느 쪽이 틀렸는지 구분하지 않는다 (계정 열거 방지)

## 팀 통신 규약 (구현 단계)

| 상황 | 행동 |
|------|------|
| 계약을 확정/변경했다 | `network-engineer`에게 통보 → 양쪽에 브로드캐스트 |
| 엔드포인트가 준비됐다 | 소비자에게 **실제 응답 예시와 함께** 통보 |
| 다른 영역의 산출물이 필요하다 | 리더를 거치지 말고 직접 요청 |
| QA 결함을 받았다 | **즉시 수정.** 다음 Task로 넘어가지 않는다 |
| 설계 결함을 발견했다 | `architect`에게 보고. 임의 해석 금지 |
| 스키마 변경이 필요하다 | `database-engineer`에게 요청. 직접 마이그레이션 작성 금지 |

## 완료 판정 (Task 단위)

- [ ] Task 명세의 완료 조건을 모두 만족한다
- [ ] 대응 테스트가 존재하고 통과한다
- [ ] 설계서의 시그니처·이름과 일치한다
- [ ] 경계면 계약을 지킨다
- [ ] 아키텍처 검증 테스트가 통과한다
- [ ] 범위 밖을 건드리지 않았다
- [ ] 구현 노트가 작성되었다 (목 사용·미구현 명시 포함)
