## 1. 계약 우선 원칙

**계약이 정본이다.** 구현이 계약과 다르면 구현을 고친다. 계약이 틀렸다면
계약을 갱신하고 **생산자·소비자 양쪽에 동시 통보**한다.

한쪽만 바꾸면 계약을 두는 의미가 없다. 이것이 이 플레이북의 존재 이유다.

### 계약 문서에 반드시 실제 응답 예시를 넣는다

타입 정의만으로는 소비자가 래핑 여부를 오해한다.
**프론트엔드 런타임 오류의 최대 원인**이다.

```markdown
### POST /api/sessions

요청: `{ "email": "a@b.com", "password": "..." }`

성공 201:
{ "data": { "sessionId": "s-1", "expiresAt": "2026-08-14T12:00:00Z" } }

실패 401:
{ "error": { "code": "INVALID_CREDENTIALS", "message": "..." } }

- 멱등: 아니오 (재시도 금지)
- 타임아웃: 연결 3s / 읽기 10s
```

## 2. 프로토콜 선택

| 프로토콜 | 적합 | 부적합 |
|---------|------|--------|
| REST | 리소스 중심 CRUD, 캐시 활용, 공개 API | 복잡한 조회 조합, 실시간 |
| GraphQL | 클라이언트마다 필요 필드가 다름, 과다/과소 조회 문제 | 단순 CRUD (과설계), 캐시 중요 |
| gRPC | 내부 서비스 간, 저지연·고빈도, 스트리밍 | 브라우저 직접 호출, 공개 API |
| WebSocket | 양방향 실시간, 고빈도 갱신 | 단방향 알림 (SSE로 충분) |
| SSE | 서버→클라이언트 단방향 스트림 | 양방향 |
| 메시지 큐 | 비동기 처리, 시스템 간 결합 완화 | 즉시 응답 필요 |

**프로토콜 변경은 ADR 대상이다.** 임의로 결정하지 않는다.

## 3. REST 계약 확정 항목

설계 단계에서 확정하고, 구현 단계에서 실측으로 검증한다.

| 항목 | 확정할 것 | 흔한 사고 |
|------|----------|----------|
| **응답 래핑** | `{data: T}` vs `T` — **전 엔드포인트 일관** | 소비자가 언랩 안 해서 `.map is not a function` |
| 네이밍 | camelCase / snake_case. **변환 지점 단 한 곳** | `thumbnailUrl` vs `thumbnail_url` |
| null 처리 | `null` 명시 vs 키 생략 | 옵셔널 체이닝 누락으로 크래시 |
| 날짜·시각 | ISO 8601 + UTC | 타임존 누락으로 하루 어긋남 |
| 목록 응답 | 배열 직접 vs `{items, total}` | 소비자가 배열로 기대 |
| 페이지네이션 | 커서 vs 오프셋, 메타 필드명 | 다음 페이지 로직 불일치 |
| 빈 목록 | `[]` (null 금지) | null 체크 누락 |
| 숫자 | 정수 vs 문자열 (큰 수) | JS 정밀도 손실 |

### 상태 코드 사용 규칙

| 코드 | 의미 | 주의 |
|------|------|------|
| 200 | 성공 + 본문 | |
| 201 | 생성됨 | `Location` 헤더 또는 본문에 식별자 |
| 202 | 접수됨 (비동기) | **최종 결과가 아님** — 5절 |
| 204 | 성공, 본문 없음 | 소비자가 파싱 시도하지 않도록 |
| 400 | 요청 형식·검증 오류 | `details`에 필드별 오류 |
| 401 | 인증 실패 | 어느 쪽이 틀렸는지 구분하지 않는다 |
| 403 | 권한 없음 | 존재 여부를 노출하지 않으려면 404 사용 검토 |
| 404 | 없음 | |
| 409 | 상태 충돌 | 낙관적 락 실패, 중복 생성 |
| 429 | 레이트 리밋 | `Retry-After` 헤더 |

## 4. 에러 규약

**엔드포인트마다 다른 에러 형태는 소비자에게 분기 지옥을 만든다.**
하나의 형태로 통일한다.

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "입력값이 올바르지 않습니다",
    "details": [
      { "field": "email", "code": "INVALID_FORMAT" }
    ]
  }
}
```

| 규칙 | 이유 |
|------|------|
| `code`는 기계 판독용 상수 | 소비자가 문구 매칭으로 분기하면 문구 변경 시 깨진다 |
| `message`는 사용자 노출 가능 수준 | 내부 구조·스택·테이블명 금지 |
| `details`는 선택. 필드별 오류에 사용 | 폼 매핑용 |
| code 목록을 계약에 나열 | 소비자가 처리할 케이스를 안다 |

## 5. 비동기 작업

**즉시 응답과 최종 결과를 별개 타입으로 정의한다.**
이 혼동이 흔한 크래시 원인이다 — 소비자가 202 응답에서 최종 결과 필드를 읽는다.

```markdown
### POST /api/exports  (비동기)

즉시 응답 202:
{ "data": { "jobId": "j-1", "status": "queued" } }

### GET /api/exports/{jobId}  (결과 조회)

진행 중 200:
{ "data": { "jobId": "j-1", "status": "running", "progress": 0.4 } }

완료 200:
{ "data": { "jobId": "j-1", "status": "done", "fileUrl": "...", "failedIndices": [] } }
```

`failedIndices`는 완료 응답에만 있다. 202 응답에서 접근하면 undefined다.
**타입을 나누면 컴파일 단계에서 잡힌다.**

결과 전달 방식(폴링 / 웹훅 / 푸시)을 계약에 명시한다.

## 6. 실시간 통신

| 항목 | 확정할 것 |
|------|----------|
| 연결 | 인증 방식(핸드셰이크 시 토큰), 연결 수립 실패 시 동작 |
| 메시지 스키마 | 타입 필드 + 페이로드. **버전 포함** |
| 재연결 | 백오프 전략, 재연결 후 누락 메시지 복구 방식 |
| 하트비트 | 주기, 미응답 시 판정 |
| 순서 보장 | 보장하는가. 아니면 시퀀스 번호로 정렬 |
| 중복 | 발생 가능한가. 멱등 처리 필요 여부 |
| 백프레셔 | 소비자가 느릴 때의 동작 |

**재연결 후 누락 메시지 복구를 설계하지 않으면** 화면이 조용히 낡은 상태로 남는다.
재연결 시 전체 상태를 다시 조회하는 것이 가장 단순하고 견고하다.

## 7. 신뢰성 정책

### 타임아웃

모든 외부 호출에 **연결·읽기 타임아웃을 건다.** 무한 대기는 커넥션 고갈로 이어진다.
값은 계약에 명시한다.

### 재시도 — 멱등성이 전제

| 요청 | 멱등 | 재시도 |
|------|------|--------|
| GET, PUT, DELETE | 예 | 가능 |
| POST | 아니오 | **멱등키 없이는 금지** |

비멱등 요청을 재시도하려면 **멱등키(Idempotency-Key)** 를 도입하고
서버가 중복을 판정하게 한다.

재시도 대상: 네트워크 오류, 5xx, 429(`Retry-After` 준수).
재시도 금지: 4xx (429 제외) — 재시도해도 같은 결과다.

백오프는 **지수 + 지터**. 지터 없이 재시도하면 동시에 몰려 서버를 다시 넘어뜨린다.

### 서킷 브레이커

연속 실패가 임계를 넘으면 일정 시간 호출을 차단한다.
실패하는 의존에 계속 요청하면 스레드·커넥션이 고갈되어 **장애가 전파**된다.

## 8. 버저닝

- 하위 호환 변경(필드 추가, 선택 파라미터 추가)은 버전을 올리지 않는다
- **하위 호환 파기**(필드 제거·이름 변경·타입 변경·의미 변경)는 새 버전
- 소비자는 **모르는 필드를 무시**하도록 구현한다. 엄격 파싱은 서버의 필드 추가를 막는다
- 구 버전 폐기는 사전 공지와 유예 기간을 두고, 계약에 폐기 예정을 명시한다

## 9. 테스트

| 대상 | 방식 | 요구 |
|------|------|------|
| 계약 준수 (생산자) | 계약 테스트 | 응답이 계약 예시와 shape 일치 |
| 계약 준수 (소비자) | 계약 테스트 | 계약 예시 응답을 정상 파싱 |
| 재시도·백오프 | 단위 | 실패 주입으로 횟수·간격 검증 |
| 타임아웃 | 단위 | 지연 주입으로 중단 확인 |
| 서킷 브레이커 | 단위 | 임계 초과 시 차단, 복구 |
| 에러 매핑 | 단위 | 각 code가 올바르게 처리됨 |
| 실시간 | 통합 | 연결·재연결·누락 복구 |

**계약 테스트를 양쪽에 둔다.** 한쪽만 있으면 다른 쪽이 어긋나도 모른다.
계약 문서의 응답 예시를 **테스트 픽스처로 공유**하면 문서와 테스트가 갈라지지 않는다.

## 경계면 검증 협력

`qa-inspector`가 경계면을 교차 검증할 때 이 계약 문서가 기준이 된다.
**불일치가 발견되면 정본 판정은 network-engineer의 책임**이다.
"양쪽이 알아서 맞추세요"로 넘기지 않는다.
