## 1. 프로세스 경계

데스크탑 앱의 핵심 구조는 **특권 프로세스(메인)와 비특권 프로세스(렌더러)의 분리**다.

```
메인 프로세스           특권: 파일 시스템, 셸, OS API, 네이티브 모듈
    ↕ IPC (좁게 정의된 브리지)
렌더러 프로세스          비특권: UI만
```

```
src/
├── main/            메인 프로세스 — IPC 핸들러, 창 관리, OS 통합
├── preload/         브리지 — 노출할 API만 정의
├── renderer/        UI — 웹 프론트엔드 구조와 동일
└── shared/          순수 로직 + IPC 타입 정의 (양쪽이 참조)
```

**비즈니스 로직을 UI 프로세스에 두지 않는다.** `shared/`의 순수 모듈에 두면
프로세스 기동 없이 테스트되고, 어느 프로세스에서든 재사용된다.

## 2. IPC 계약

**IPC 경계는 API 계약과 동등하게 취급한다.** 데스크탑 앱의 최대 결함 지점이다.
양쪽이 서로 다른 shape을 가정하면 런타임에 터지고, 타입 검사로는 잡히지 않는다.

### 타입을 한 곳에 정의한다

```typescript
// shared/ipc-contract.ts — 메인과 렌더러가 모두 참조
export interface IpcContract {
  "file:open":  { req: { filters: FileFilter[] }; res: { path: string; content: string } | null };
  "file:save":  { req: { path: string; content: string }; res: { ok: true } | { ok: false; error: string } };
}
```

### 채널 목록을 문서화한다

`impl-notes-frontend-desktop.md`에 반드시 기록한다:

| 채널 | 방향 | 요청 | 응답 | 특권 |
|------|------|------|------|------|
| `file:open` | 렌더러→메인 | `{filters}` | `{path, content} \| null` | 파일 읽기 |
| `app:update-available` | 메인→렌더러 | - | `{version, notes}` | - |

`qa-inspector`가 이 표와 실제 핸들러·호출부를 대조한다.

### 규칙

- 채널 이름에 네임스페이스를 쓴다 (`domain:action`)
- 요청·응답은 **직렬화 가능한 평문 데이터**만. 함수·클래스 인스턴스 금지
- 에러를 응답 타입에 포함한다. IPC 경계에서 예외를 던지면 정보가 소실된다
- 메인→렌더러 푸시(이벤트)는 구독 해제를 반드시 구현한다 — 창 재생성 시 누수

## 3. 보안

**렌더러에 특권을 주지 않는다.** 렌더러는 원격 콘텐츠를 렌더링할 수 있으므로
신뢰 경계 밖으로 취급한다.

| 항목 | 요구 |
|------|------|
| Node 통합 | 렌더러에서 **비활성**. 활성화는 보안 결함으로 간주 |
| 컨텍스트 격리 | **활성.** preload에서 좁게 정의한 API만 노출 |
| 노출 API | 범용 `invoke(channel, args)` 금지. 채널별 전용 함수만 |
| 원격 콘텐츠 | 로드한다면 별도 프로세스 + 엄격한 CSP |
| 파일 경로 | 렌더러가 준 경로를 검증 없이 열지 않는다 (경로 탈출 방지) |
| 셸 실행 | 사용자 입력을 셸 명령에 넣지 않는다 |

```typescript
// preload — 좋음: 채널별 전용 함수
contextBridge.exposeInMainWorld("api", {
  openFile: (filters) => ipcRenderer.invoke("file:open", { filters }),
});

// 나쁨 — 렌더러가 임의 채널을 호출할 수 있다
contextBridge.exposeInMainWorld("api", { invoke: ipcRenderer.invoke });
```

## 4. 로컬 자원

### 저장 위치를 명시한다

플랫폼마다 다르므로 **impl-notes에 반드시 기록**한다.

| 데이터 | 위치 | 비고 |
|--------|------|------|
| 설정 | OS 표준 앱 데이터 경로 | 하드코딩 금지, API로 조회 |
| 캐시 | OS 표준 캐시 경로 | 삭제되어도 동작해야 함 |
| 사용자 문서 | 사용자가 지정한 경로 | 앱 데이터에 넣지 않는다 |
| 비밀·토큰 | **OS 자격증명 저장소** | 평문 파일 금지 |

### 파일 접근

- 대용량 파일은 스트리밍한다. 전체를 메모리에 올리지 않는다
- 쓰기는 **임시 파일 → 원자적 교체**로. 중간에 종료되어도 손상되지 않는다
- 파일 잠금·동시 접근(같은 앱 다중 실행)을 고려한다

## 5. OS 통합

| 기능 | 주의 |
|------|------|
| 트레이·메뉴바 | 플랫폼별 동작 차이가 크다. `platform/` 어댑터로 분리 |
| 전역 단축키 | 다른 앱과 충돌 가능. 변경 가능하게 |
| 알림 | 권한 필요. 거부 경로 구현 |
| 파일 연결 | 설치 시 등록. 제거 시 정리 |
| 창 상태 | 위치·크기 복원. 모니터 제거 시 화면 밖 배치 방지 |
| 딥링크 | 프로토콜 등록. 앱 실행 중/미실행 양쪽 처리 |

## 6. 테스트

| 대상 | 방식 | 요구 |
|------|------|------|
| `shared/` 순수 로직 | 단위 | 프로세스 기동 없이 |
| IPC 핸들러 | 통합 | 요청 → 응답 shape 검증. **양쪽 타입 대조** |
| 렌더러 UI | 컴포넌트 | 웹 프론트엔드와 동일 |
| 파일·OS 접근 | 통합 | **임시 디렉토리로 격리** |
| 사용자 시나리오 | E2E | headless |

**테스트가 실제 사용자 데이터 디렉토리를 건드리지 않게 한다.**
테스트마다 격리된 앱 데이터 경로를 지정한다.

## 7. E2E silent 설정

`harness/principles/testing.md` 3절 필수 준수.

| 도구 | 설정 요지 |
|------|----------|
| Playwright for Electron | `_electron.launch()`, CI에서 가상 디스플레이 |
| WebdriverIO + electron-service | headless 설정, JUnit 리포터 |
| Tauri (WebDriver) | `tauri-driver` + 가상 디스플레이 |

### 공통 규칙

- 창을 화면에 띄우지 않는다. 가상 디스플레이(Xvfb 등) 또는 headless 모드
- **테스트마다 격리된 사용자 데이터 디렉토리**를 환경 변수로 지정
- 기계 판독 리포터 필수. 실패 시에만 스크린샷
- 고정 `sleep` 금지 — 조건 기반 대기
- 앱 종료를 명시적으로 수행한다. 좀비 프로세스가 CI를 점유한다

**headless 실행이 불가능한 환경이면** E2E를 작성하되 실행은 건너뛰고
**미실행을 명시**한다.

## 8. 패키징과 배포

`devops-engineer`와 협의할 사항. 구현 중 확인되면 impl-notes에 기록한다.

| 항목 | 확인 |
|------|------|
| 대상 플랫폼 | Windows / macOS / Linux 중 어디까지 |
| 코드 서명 | 인증서 보유 여부. macOS 공증 필요 여부 |
| 자동 업데이트 | 필요 여부, 업데이트 서버 |
| 설치 형식 | 인스톤러 / 포터블 / 스토어 |
| 네이티브 모듈 | 플랫폼별 빌드 필요 여부 |

**인증서가 없으면 서명 없이 빌드하고 그 사실을 명시한다.** 임의로 우회하지 않는다.

**특정 OS에서만 재현되는 문제는 해당 OS를 명시**하고, 확인 불가한 OS는
**미검증으로 보고**한다. 전 플랫폼 정상이라고 단정하지 않는다.
