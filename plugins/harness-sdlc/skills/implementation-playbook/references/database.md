## 1. 스키마 설계

### 네이밍

**설계서의 컬럼명 ↔ 도메인 필드명 매핑 표가 정본이다.** 임의로 바꾸면
매퍼와 어긋나고, `qa-inspector`가 결함으로 검출한다.

| 항목 | 관례 (기존 코드가 우선) |
|------|----------------------|
| 테이블 | 복수형 snake_case (`users`, `order_items`) |
| 컬럼 | snake_case |
| 기본키 | `id` |
| 외래키 | `{단수형}_id` (`user_id`) |
| 불리언 | `is_`/`has_` 접두 |
| 시각 | `_at` 접미 (`created_at`) |
| 인덱스 | `idx_{테이블}_{컬럼들}` |

### 타입 선택

| 데이터 | 권장 | 이유 |
|--------|------|------|
| 금액 | 정수(최소 단위) 또는 decimal | **부동소수 금지.** 반올림 오차 |
| 시각 | 타임존 포함 타입, UTC 저장 | 지역 시각 저장은 서머타임에서 깨진다 |
| 식별자 | UUID 또는 시퀀스 | 외부 노출 시 UUID (열거 방지) |
| 열거값 | 문자열 + CHECK 제약 | DB enum은 값 추가 시 마이그레이션 필요 |
| JSON | 구조가 불명확한 부속 데이터만 | 쿼리·제약 대상이면 컬럼으로 분리 |

### 필수 컬럼

- `created_at`, `updated_at` — 예외 없이
- 소프트 삭제가 필요하면 `deleted_at`. **단, 모든 쿼리에 조건이 붙는 부담**을
  감수할 가치가 있는지 먼저 검토한다
- 낙관적 락이 필요하면 `version`

## 2. 마이그레이션

### 원칙

- **후퇴(down) 경로가 없는 마이그레이션은 작성하지 않는다.** 불가능하면
  (데이터 파괴적 변경) 그 사실을 명시하고 승인을 받는다
- 하나의 마이그레이션 = 하나의 논리적 변경
- **마이그레이션 파일을 수정하지 않는다.** 이미 적용된 것을 고치면 환경 간
  스키마가 갈라진다. 새 마이그레이션을 추가한다
- 스키마 변경과 데이터 변경을 분리한다

### 작성 체크리스트

- [ ] 전진(up)과 후퇴(down)가 모두 있다
- [ ] 전진 → 후퇴 → 전진 왕복이 성공한다 (테스트로 검증)
- [ ] 대용량 테이블 변경 시 락 범위와 예상 소요를 기록했다
- [ ] 애플리케이션 배포와의 순서 의존을 명시했다
- [ ] 롤백 시 데이터 손실 여부를 명시했다

### 배포 순서 의존

마이그레이션과 애플리케이션 배포의 순서를 반드시 명시한다.

| 변경 | 순서 |
|------|------|
| 컬럼 추가 (nullable) | 마이그레이션 → 앱 배포 |
| 컬럼 추가 (NOT NULL) | 3단계 (3절 참조) |
| 컬럼 제거 | 앱 배포(사용 중단) → 마이그레이션 |
| 인덱스 추가 | 무관 (온라인 생성 사용) |

## 3. 파괴적 변경의 단계적 수행

컬럼 삭제·이름 변경·타입 변경을 **한 번에 하지 않는다.** 배포 중 구/신 버전이
공존하는 순간에 반드시 깨진다.

### 컬럼 이름 변경 (5단계)

| 단계 | 작업 | 배포 |
|------|------|------|
| 1 | 새 컬럼 추가 (nullable) | 마이그레이션 |
| 2 | 앱이 양쪽에 쓰기 | 앱 배포 |
| 3 | 기존 데이터 백필 | 마이그레이션 (배치) |
| 4 | 앱이 새 컬럼만 읽기 | 앱 배포 |
| 5 | 기존 컬럼 제거 | 마이그레이션 |

각 단계 사이에 **되돌릴 수 있는 지점**이 있다. 이것이 단계로 나누는 이유다.

### NOT NULL 추가 (3단계)

1. nullable로 추가
2. 기존 행 백필 + 앱이 항상 값을 채우도록 배포
3. NOT NULL 제약 추가

### 대용량 테이블 주의

- 락이 걸리는 DDL은 서비스 중단을 만든다. 온라인 스키마 변경 도구를 검토한다
- 백필은 배치로 나눈다. 한 트랜잭션에서 수백만 행을 갱신하지 않는다
- 예상 소요와 락 범위를 impl-notes에 기록하고 `devops-engineer`에게 전달한다

## 4. 인덱스

**근거 없이 추가하지 않는다.** 인덱스는 읽기를 빠르게 하고 쓰기를 느리게 한다.

### 추가 절차

1. 대상 쿼리를 특정한다
2. 실행 계획을 확인한다 (인덱스 전)
3. 인덱스를 추가한다
4. 실행 계획을 다시 확인한다 (개선 확인)
5. **대상 쿼리와 개선 결과를 impl-notes에 기록한다**

### 설계 요령

| 상황 | 인덱스 |
|------|--------|
| 등호 + 범위 조건 혼합 | 등호 컬럼을 앞에, 범위를 뒤에 |
| 정렬 포함 | 정렬 컬럼을 인덱스 끝에 (방향 일치) |
| 커버링 가능 | 조회 컬럼을 포함시켜 테이블 접근 제거 |
| 부분 데이터만 조회 | 부분 인덱스 (조건부) |
| 외래키 | 참조 무결성 검사·조인 성능을 위해 대개 필요 |

**중복 인덱스를 만들지 않는다.** `(a)` 인덱스는 `(a, b)`가 있으면 불필요하다.

## 5. 쿼리

- **N+1을 만들지 않는다.** 루프 안의 쿼리를 조인 또는 일괄 조회로 바꾼다
- `SELECT *`를 쓰지 않는다. 컬럼 추가 시 예상치 못한 데이터가 흘러들어온다
- 페이지네이션은 **커서 기반**을 우선한다. 오프셋은 깊은 페이지에서 느려진다
- 사용자 입력을 문자열 연결로 쿼리에 넣지 않는다. **바인딩 파라미터만**
- 트랜잭션을 짧게 유지한다. 트랜잭션 안에서 외부 호출 금지

---

## 6. 정합성

**정합성은 애플리케이션이 아니라 DB에서 보장한다.**
애플리케이션 검증은 사용자 경험용이지 보증이 아니다 — 배치·수동 수정·다른
서비스가 우회할 수 있다.

| 제약 | 사용 |
|------|------|
| NOT NULL | 값이 반드시 있어야 하는 컬럼 전부 |
| UNIQUE | 업무상 유일한 값 (이메일, 주문번호) |
| FOREIGN KEY | 참조 무결성. `ON DELETE` 동작을 명시적으로 결정 |
| CHECK | 값 범위, 열거값, 상태 조합 |

**`ON DELETE CASCADE`를 습관적으로 쓰지 않는다.** 의도치 않은 대량 삭제의
원인이다. 삭제 정책은 도메인 결정이므로 설계서에서 확정한다.

## 7. 테스트

| 대상 | 방식 | 요구 |
|------|------|------|
| 마이그레이션 | 통합 | **전진 → 후퇴 → 전진 왕복** |
| 제약 | 통합 | 위반 데이터 삽입 시 실패하는지 |
| 쿼리 | 통합 | 실제 DB로 결과 검증 |
| 성능 민감 쿼리 | 통합 | 대표 규모 시드로 실행 계획 확인 |
| 매퍼 (백엔드 협업) | 단위 | 컬럼명 ↔ 필드명 왕복 |

### 인메모리 DB로 대체하지 않는다

SQLite로 PostgreSQL을 대체하면 방언 차이(타입, 제약 동작, 함수, 트랜잭션
격리) 때문에 **통과한 테스트가 프로덕션에서 실패한다.** 컨테이너로 실제
엔진을 띄운다.

### 격리

- 테스트마다 트랜잭션 롤백 또는 스키마 초기화로 격리한다
- 테스트 간 순서 의존을 만들지 않는다

---

## 프로덕션 접근 금지

- **프로덕션 DB에 직접 접근하지 않는다**
- 마이그레이션 실행은 **사용자 승인 후 `devops-engineer`**가 수행한다
- DB 컨테이너를 띄울 수 없어 검증하지 못했다면 **미실행으로 명시한다.**
  검증되지 않은 마이그레이션을 검증됐다고 보고하지 않는다
